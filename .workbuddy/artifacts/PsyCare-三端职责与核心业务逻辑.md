## 一、总体结构：一套后端，三个前端端口

后端 7 个 Controller、4 大引擎已完整实现（见 `psycare-server/README.md`）。三端不是三套系统，而是**同一份数据 + 同一套接口 + 三种角色视图**：

| | 数据可见范围 | 核心动作 | 能否看个案 |
|---|---|---|---|
| 居民端 | 仅本人 | 测评、问诊、预约 | 仅本人 |
| 医生端 | 辖区内 + 指派给本人的工单 | 处置工单、接诊、随访 | 是（授权范围内） |
| 管理端 | 全域，但**去标识化** | 配置规则、监管工单、看统计 | 否（只看统计） |

这条边界决定了三端的页面形态：居民端是**引导式自助流程**（宽留白、少选项、强提示），医生端是**待办驱动的工作台**（左列表 + 右详情，主导航 6 项固定），管理端是**数据密集的驾驶舱**（4 指标 + 2 图表 + 状态汇总）。

## 二、三端职责与功能模块

### 1. 居民端（社区 Web 端 · 面向居民本人）

**职责**：自助完成心理测评并读懂结果，在需要时获得 AI 陪伴与合适的医生资源。入口遵循「先测评、再分诊」，不假设用户懂心理学。

| 功能模块 | 关键页面 | 说明 |
|---|---|---|
| 首页工作台 | 欢迎横幅 + 心理状态环 + 快捷入口 + 趋势/通知 | 一屏回答「我现在什么状态、下一步做什么」 |
| 量表浏览与作答 | 测评中心、问卷作答 | 分类筛选、逐题聚焦作答、进度条、可保存稍后继续 |
| 风险分级与结果反馈 | 测评结果与反馈 | 见第三章链路 A |
| AI 智能问诊 | 会话页 + 上下文侧栏 | SSE 流式逐字输出，自动引用关联测评 |
| 医生推荐与预约 | 医生推荐 | 见第三章链路 B |
| 历史趋势与站内通知 | 我的记录、通知列表 | 时间线看变化；测评/问诊/讲座三类通知 |

### 2. 医生端（社区医生工作台 · 面向精神科医师与咨询师）

**职责**：承接系统分发的预警工单与居民问诊，完成从确认到结案的闭环随访；对辖区内高风险居民保持主动关注，**不做重复登记**。

| 功能模块 | 关键页面 | 说明 |
|---|---|---|
| 预警工单处置 | 工单列表 + 详情 + 处置区 + 流转日志 | 待办驱动；状态机按钮按当前状态动态渲染 |
| 居民档案与随访记录 | 档案页 | 基本信息 + 历次测评 + 随访记录 |
| 图文与电话问诊 | 问诊工作台 | `consult_session` 已预留 DOCTOR 类型 |
| 出诊排班与负载设置 | 排班管理 | 负载值直接影响推荐排序（负载惩罚项） |
| 个人资料与专长维护 | 个人设置 | 专长标签是推荐匹配的关键输入 |

### 3. 管理端（街道管理后台 · 面向管理员与运营）

**职责**：配置量表与计分规则、监管全域预警工单、查看去标识化统计。**不介入个案诊疗**，只负责规则、权限与运营。

| 功能模块 | 关键页面 | 说明 |
|---|---|---|
| 数据驾驶舱 | 4 指标 + 30 天趋势 + 风险分布 + 工单状态汇总 | 对应待新增的 4 个 `AdminController` 统计接口 |
| 预警工单监管与督办 | 全量工单表 | 与医生端复用同一套状态机组件，多一层督办视角 |
| 量表与计分规则配置 | 量表管理 | 切分点、反向计分、危机项**全部入库可配**，不写死代码 |
| 居民档案与权限管理 | 居民管理 | 单独同意记录、脱敏策略、账号状态 |
| 医生排班与操作审计 | 医生管理 + 审计日志 | 敏感接口 AOP 审计 |

## 三、核心业务逻辑

### 链路 A：测评闭环（系统的起点）

```
居民填答量表
  → POST /api/assessment/submit
     ① 校验量表 / 题目 / 作答完整性
     ② ScoringEngine.score
          · 按 scoring_rule 切分点计分（数据驱动，不硬编码）
          · 反向计分题：该题最大选项分 − 选项分
          · 危机项（PHQ-9 第 9 题）得分 > 0 → 风险等级强制 D
          · 输出 总分 + 原始等级 + ABCD + 危机标记
     ③ 落库 assessment + assessment_answer
     ④ AlertEngine.evaluate → 可能生成工单
          · CRISIS    危机项阳性（最高优先级）
          · THRESHOLD 单次达到 B / C / D
          · TREND     时间窗口内相邻两次总分涨幅超阈值
          · 幂等：同居民同类型 PENDING 工单不重复创建
     ⑤ 返回 AssessmentResultResponse（等级 + 分维度 + 建议文案）
```

**结果页要回答三件事**（对应设计稿 S5）：
1. **我几级**——`B` 大字 + 「中风险 · 建议 2 周内复测」+ 总分/阈值项数/危机项状态；A→B→C→D 标尺上高亮当前档位，让「分级」这件事可见。
2. **为什么**——「各维度得分明细」按分数排序的横向条，超出阈值的用琥珀/陶土色标注；脚注声明规则来自管理端配置。
3. **然后呢**——结论文案 + 3～4 条调适建议 + 三个出口（带着结果去 AI 问诊 / 查看推荐医生 / 查看作答明细）。

`assessment.id` 是后续问诊、推荐、预警的**关联锚点**——这就是「测评驱动」。

### 链路 B：AI 问诊 + 医生推荐（需求二的核心）

```
POST /api/ai-consult/open   （可关联 assessmentId / alertId）
POST /api/ai-consult/chat   （SSE 流式）
  ① 用户输入先过 CrisisDetector —— 本地规则，不依赖模型自觉
       命中 → 不走模型，返回固定危机文案（含援助热线）+ 创建 CRISIS 工单转人工
       未命中 → PromptBuilder 注入测评上下文 → DeepSeekClient 流式调用
              → 逐 token 透出 → 完整回复侧再检测一次 → 落库
POST /api/ai-consult/{id}/close   （结束会话，顺势接推荐）

GET /api/recommend/doctors?sessionId=&topN=3
  → 取最近测评的等级 / 突出维度
  → RecommendationEngine 三级匹配 + 加权排序
       科室优先级（风险等级 → 目标科室）
       + 专长标签匹配（测评维度 → 医生标签）
       + 评分加成 − 负载惩罚
  → 写入 recommendation_log.reason → 返回
```

**设计稿如何体现「可解释的推荐」**（S7）：每位医生卡片中间固定一格**推荐理由**（灰底区分），写明命中了哪两个维度、科室优先级如何、负载与评分如何参与排序；页脚声明结果由 `RecommendationEngine` 计算并落库 `recommendation_log`，可回溯。医生端与管理端因此能回答「为什么给这位居民推荐了这位医生」。

**AI 问诊页的双栏设计**（S6）：左侧对话，右侧是**本次问诊上下文**——关联测评卡（等级/总分/查看完整报告）、危机识别与转人工提示卡（含 12356 热线）、AI 推荐的医生卡。这样用户不必重复描述，AI 的引用有出处（气泡内「依据：…」小字）。

### 链路 C：预警处置状态机（医生端/管理端共用）

```
PENDING ──→ CONFIRMED ──→ PROCESSING ──→ FOLLOWED ──→ CLOSED
   └────→ REJECTED
```
- 后端只接受合法流转，非法直接 400；前端按当前状态**只渲染合法下一状态**的按钮。
- 每次流转写 `alert_status_log`，处置备注一并落库，全程可追溯。
- 设计稿 S8 的右栏顺序与这条链路的认知顺序一致：**触发原因 → 工单处置 → 流转日志**。

### 安全与合规红线（不可妥协）

1. 危机词检测**必须本地规则实现**，不能靠模型自觉。
2. AI 不诊断、不开药，回答带边界声明；危机输入强制转人工。
3. 心理数据属敏感个人信息：单独同意、展示脱敏、统计去标识化。
4. 生产环境更换 `jwt.secret`，密码只用 BCrypt 哈希。

设计上的落点：测评中心的「测评须知 / 合规提示」卡、总览页的「数据权限与合规边界」卡、管理端图表下方的去标识化图注，三处都在界面上把红线说出来，而不是藏在文档里。
