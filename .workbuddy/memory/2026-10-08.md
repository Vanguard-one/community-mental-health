## 已核实的技术事实（替代凭记忆）

1. **Milvus REST v2 原生支持 BM25 Function** —— 官方 cURL 示例确认：
   `POST /v2/vectordb/collections/create`，body 里 `schema.functions=[{type:"BM25",inputFieldNames:["text"],outputFieldNames:["sparse"]}]`。
   → **探针可以零依赖**（标准库 urllib），不必装 pymilvus。
2. **中文分词必须显式配**：`analyzer_params = {"tokenizer":"jieba","filter":["cnalphanumonly"]}`，
   等价内置快捷 `{"type":"chinese"}`。字段级配置放在 REST 的 `elementTypeParams` 里
   （**确切 key 名尚未实测**，探针跑到断言 2 才能确认）。
3. **通义 OpenAI 兼容接口不支持 sparse 输出**：传 `output_type=sparse` 会 **HTTP 200 但 embedding 为空**
   （静默失败）。本项目不需要它 —— 稀疏向量由 Milvus 的 BM25 生成。
4. **Milvus REST 失败也走 HTTP 200 + body 里的 `code`**（成功码 0 或 200）—— 与项目硬约定 #2 同一形状。

### 三、验收程序当场抓到的两个真 bug（只有真跑才暴露）

1. **`DataBufferLimitException`：WebClient 默认只缓冲 256 KB**，而 25×1024 维的批量响应**实测 484 KB**。
   单条响应仅 ~19 KB → **只测单条永远发现不了**。且 `retrieve()` 把它包成
   `WebClientResponseException(200)`，经 `LlmErrorMapper` 只剩一句「上游 200：」——把人往「上游故障」引。
   → 按 `batchSize*dim*24 + 1MB` 推算缓冲（下限 4 MB / 上限 64 MB），并在 `mapUpstreamError` 里
   把「2xx 却失败」单独说清。
2. **百炼的 `index` 字段不可信**：25 条批量里**每个元素都返回 `"index": 0`**（字段有、类型对、值恒定）。
   照它回填 → 全部向量写到下标 0，现象只是一句与内容无关的「第 1 条向量缺失」，而 HTTP 层完全正常。
   数组顺序本身是对的（**交叉验证**：批量[0]↔单独第1条 cos=1.000000、批量[24]↔单独第25条 cos=1.000000）。
   → 规则改为「`index` 构成 0..n-1 的合法排列时才信它，否则退回数组顺序」。

### 四、另一个必须记住的事实：**向量不可逐位复现**

同一文本：两次单条调用**逐位相同**；但**作为 25 条批的成员时**会得到 **cos≈0.9978** 的另一版本
（对照：不同文本 cos≈0.864，所以不是错位）。与批大小无关（n=2/16/20/21/24/25 都有，n=10 恰好相同），
是服务端内部路径差异。
→ **校验脚本只能用相似度阈值（≥0.99），不能拿「向量相等 / MD5 相等」当判据。**

### 九、用户问「synthetic_corpus.jsonl 是干什么的」→ 顺带查出并修掉一个真缺陷（11:12）

**交付物**：`gen_synthetic_corpus.py` 的调用守卫生效修复 + 语料全量重生成。

**发现的缺陷**：回答「这份语料干什么用」时顺手核对生成约束是否真的生效，结果发现
**81 条里有 11 条正文是断在半句处的**（最短 **23 字**：「很多人在服药一段时间后，会冒出这样的念头：感觉」），

全程没有任何一处会报错。

**修法**（`gen_synthetic_corpus.py`）：
1. `max_tokens` 2048 → **4096**；
2. 新增 `finish_reason == "length"` → 抛异常、走重试；

4. 失败条目不写文件（保留续跑语义）。

## 14:00 AI 助手模块定位判定（纯咨询，未改代码）

用户问：当前 AI 助手是「一问一答」还是「Agent（自主思考 → 行动 → 反馈 → 再思考）」；AI 问诊是否需要 Agent。

**核实**（读 `application.yml` + 全量 grep `tool_call|AiTool|ToolRegistry|agent`）：
① 对话模型 `deepseek-flash`（DeepSeek-V4.1-Flash）**是推理模型**，有 `reasoning_content` + `effort: low`
   —— 即**单次调用内已有 CoT**。这是 inference-time reasoning，**不是 Agent**；
② 全项目**无 function calling / tool_calls / AiTool / ToolRegistry 代码**，唯一命中是 `AiChatClient`
   注释里「接入 function calling 时 `delta.tool_calls` 也属于流里的帧」的预留说明。

**判定**：当前是**编排式（orchestrated）AI 应用**，档位 =「多轮记忆 + 提示词分层 + 确定性工作流」，
RAG（Phase 4）补齐后到「检索增强 + 编排」。**不是 Agent** —— 判据是**「谁在决定下一步」**：
现在是 `StageRules` / `ReferralRules` / 危机词短路由**代码**决定，模型只在给定上下文里生成。

**成熟度阶梯与建议止步线**：L1 单轮 → L2 多轮+记忆 → L3 RAG → **L4 编排式工作流（★当前）**
→ L5 受约束工具调用（Phase 5 目标）→ L6 自主 Agent（**医疗场景不建议**）。
理由：诊断 / 用药 / 危机判断要求**可审计、可复现、确定性**；自主循环带来不可复现、可能绕过安全闸门、
成本与延迟不可控、出错无法定责。正名应叫 **bounded tool use（受约束工具调用）/ 可审计编排**，
与本项目 Phase 5 的设计（两阶段调用循环 + 白名单 + `ToolContext` 服务端注入 userId +
`ai_tool_call_log` 审计 + 危机词本地短路）完全一致 —— 即「模型决定用哪个工具，代码决定边界与闸门」。
