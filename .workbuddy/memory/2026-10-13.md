### 1. 用户头像：与账号头像「同数据 + 同配方」

- 新增 `userInitial` computed = `(authStore.realName || '居').charAt(0)`
  —— 与 `DefaultLayout.vue` 的 `avatarText` **逐字一致**（同数据源、同兜底字）。两处写法必须同步，
  否则会出现「顶栏显示『居』、消息里显示别的字」的自相矛盾画面。
- 模板写在**气泡之后**：
  `<span v-if="m.role === 'user'" class="msg-face">{{ userInitial }}</span>`
- 新增样式 `.msg.user .msg-face`，**覆盖** `.msg-face` 的四项：

| 属性 | `.msg-face`（AI 默认） | `.msg.user .msg-face`（用户） | 理由 |
|---|---|---|---|
| `background` | `var(--grad-primary)` 渐变 | `var(--primary)` 实心 | 与顶栏 `.avatar` 同款；渐变是「AI 的身份表达」 |
| `font-family` | `var(--font-mono)` | `var(--font-sans)` | 中文单字用等宽发怪 |
| `font-size` | `10px`（给 `AI` 两字母） | `13px` | 单字要略大才不显小 |
| `margin` | `3px 10px 0 0`（右侧留白） | `3px 0 0 10px`（镜像） | 用户在气泡右边 |

⚠️ **两个坑**：
① **DOM 顺序即视觉顺序**：`.msg.user` 是 `justify-content: flex-end`，头像若写在气泡**之前**会跑到
气泡**左边**（与 AI 侧同侧），一眼就是错的。所以挂在气泡**之后**。
② **复用 class ≠ 长得一样**：`.msg-face` 的默认样式本来就是给 AI 的，用户侧不显式覆盖那四项，
就会得到「和 AI 同一张脸」，与「跟账号头像一样」的需求正好相反。

## 五、修「账号管理」表头「操作」与下方按钮不对齐

### 1. 现象与根因

用户反馈：`/admin/accounts` 列表表头的「操作」没有对齐下方的按钮。

**同一列两行错开** —— 表头「操作」贴列左缘，数据行的按钮却靠右。

根因是 `.ta-right` 的写法：

```css
.ta-right { justify-content: flex-end; }   /* 原・只这一条 */
```

`justify-content` **只对 flex / grid 容器生效**。而这个类在两处落脚，两处的身份不同：

| 使用处 | 标签 | 身份 | `justify-content` 是否生效 |
|---|---|---|---|
| 数据行 `AccountManage.vue:129` | `<div class="cell ta-right">` | `.cell` 是 `display:flex` → **flex 容器本身** | ✓ 生效 |
| 表头 `AccountManage.vue:71` | `<span class="ta-right">操作</span>` | `.grid-head` 是 grid 容器 → 它是**网格项（grid item）**，自身不是容器、子内容（纯文本）也不是 flex item | ✗ **完全无效** |

所以表头文字按默认块级排版贴在本列左边缘，与右对齐的按钮错开。**这就是本次的问题**。

### 2. 修法（`src/views/admin/AccountManage.vue`）

```css
.ta-right {
  justify-content: flex-end;   /* 数据行那一支：.cell 是 flex 容器 */
}

.grid-head .ta-right {
  text-align: right;           /* 表头那一支：它是网格项 */
}
```

**为什么用 `text-align` 而不是 `justify-self: end`**：网格项默认 `justify-self: stretch`，会撑满整列；`text-align: right` 让文字右缘落在列的右边界上 —— 与 `.cell` 里按钮组（`.ops` 也是 `justify-content:flex-end`）的右缘**同受** `.grid-*` 的 `padding: 12px 18px` 约束，两者齐平。改用 `justify-self: end` 会让网格项**收缩到内容宽度**，将来给表头加悬停底色或分隔线时会露出一块只有文字宽的色块。

### 3. 全项目排查

三处「表头 + `grid-head` + `ta-right`」的写法都存在，逐一核对 `.ta-right` 定义：

| 页面 | `.ta-right` 定义 | 表头是否正确 |
|---|---|---|
| `admin/AccountManage.vue` | `justify-content: flex-end` | ✗ **漏了 text-align（本次修复）** |
| `admin/BannerManage.vue` | `align-items: flex-end; text-align: right` | ✓ |
| `admin/KnowledgeBase.vue` | `text-align: right`（数据行另有 `.cell.ta-right { align-items: flex-end }`） | ✓ |

结论：**不是配色或间距问题，而是「三处同款表格只有一处写法不完整」**。另两页的数据行之所以用 `align-items: flex-end` 而不是 `justify-content`，是因为它们的 `.cell` 是 `flex-direction: column`（交叉轴即横向），所以横向对齐靠 `align-items`。

### 4. 自检

`vue-tsc -b` 退出码 0；`vite build` ✓ 2.13s；`vendor-antd` **788.18 kB**（与上一轮一致，纯 CSS 改动）。
产物核对：`AccountManage-*.css` 里 `ta-right` 精确 **2 条**规则 ——
`.ta-right[data-v-ba288fd9]{justify-content:flex-end}` + `.grid-head .ta-right[data-v-ba288fd9]{text-align:right}`（无重复、无残留）。

**待用户验收**（dev server 刷新即可，**不必重启后端**）：表头「操作」的右缘应与该列最右侧按钮（通常是「删除」）的右缘齐平；
另两页（轮播图管理 / 知识库）本来就没问题，可一并扫一眼确认。

> 💡 由此提炼 **硬约定 #121**：同一个对齐工具类要同时服务 flex 容器与 grid 项时，横向对齐必须**同时**给
> `justify-content`（flex 容器）与 `text-align`（grid 项/块级）—— 只写一条会在另一半场景下**静默失效**。

## 八、示例页 v4 —— 两栏比例 2:3 + 身份图标改「描边墨色」（**仍零项目代码改动**）

### 1. 关键结构结论：比例怎么改才「宽度恒定」

用户要求「操作页 : 简介页 = 2:3，且切换/并列时比例一致」。**不能**给两屏各写一套宽度
（滑过去再变宽会形变），正确做法是**让宽度与位置解耦**：

| 元素 | 值 | 说明 |
|---|---|---|
| `.auth-frame` | 976 → **1120px** | 40% 后表单只剩 440px，卡不加宽输入框会掉到 300px 以下 |
| `.auth-action` | `left:60%; width:40%` | 白板 440px，**恒定** |
| `.auth-action.is-form` | `translateX(-150%)` | ⚠️ 不再是 -100%：位移 = 卡宽 60% ÷ 自身宽 40% |
| `.brand-text` | `width:60%`，`.right{left:40%}` | 两份简介层都是 660px，**恒定** |

- 白板左边缘初始在 660px → 位移 -1.5×440 = -660 → 落到 0 ✓（**改比例必须同改这一处位移量**）
- 卡宽 1100（1120 − 两侧 10px 框）→ 白板内容 440−72 = 368px，简介内容 660−84 = 576px
- `.screen` padding 44/46 → **40/36**（白板收窄后要给内容让位）
- `.role-item` padding 13/16 → 12/14；hover 去掉 `translateY(-1px)`、阴影压平至 `0 4px 14px .10`

### 2. 身份图标 → 「描边墨色」（新增独立类 `.role-ico`，**不动 `.role-avatar`**）

所以**不能改它**，而是新建只在登录页身份区使用的 `.role-ico`。

三条统一（用户明确要求「统一线宽、圆角与颜色」）：

- `viewBox="0 0 24 24"` 同一栅格（原 RoleAvatar 是 96 栅格填充式）
- `stroke-width="1.8"`（22px 渲染下约 1.65px，与全站线性图标一致）
- `stroke-linecap/linejoin="round"`

### 4. ⚠️ 五个必须记住的坑

1. **`fill:both` 必须配 `cancel()` 收尾** —— 否则 WAAPI 效果（在 CSS 层叠之上）会**长期压掉
   元素自身的 `:hover` transform**。做法：`onfinish → a.cancel() + add('anim-done')`
2. **`.anim-done` 里绝不能写 `transform:none`** —— 它 (0,3,0) 会反压 `.role-item:hover`、
   `.brand-feats li:hover` 这些 (0,2,0) 的悬停位移。只写 `opacity:1`
3. **CSS 前置态只留 `opacity`，位移全部交给动画关键帧** —— 若前置态写 `translateX(24px)`，
   `cancel()` 瞬间计算值会从 24px 跳回自然态，元素上若有 transform transition 就**多播一次回弹**。
   （skill 原模板可以那么写，因为 PPT 元素不参与 hover —— 这是**刻意差异**）
4. **前置态必须在 head 里挂** —— 放 body 末尾会出现「内容先画一帧 → 再隐藏 → 淡入」的闪烁；
   head 那段与引擎的判定条件**必须逐条一致**（挂了类而引擎不启动 = 内容被永久藏住）
5. **`data-anim` 元素若没被任何 recipe 覆盖 → 前置态 `opacity:0` 会让它永久不可见**。
   已核对：login 的 7 类元素全部在 `brand-intro` 覆盖范围内

另：`countUp` 必须**在元素还不可见时先归零**（卡仍是 opacity:0），否则会看到「12 跳成 0」；
结尾必写回精确值，防中断停在中途。

原 `.view.is-shown .content-inner > * { animation: rise ... }` + `nth-child` 机械延迟 ——

## 十、点阵场「更密 + 更明显地自主运动」参数重调（2026-10-13，v6）

用户反馈原话：「我记得这个蓝色背景的白点是会自主动的，而且挺密集的，你有办法再改一下吗」。
诊断出**两个真问题**，第二个比第一个影响更大：

| 观感 | 根因（数值层面） |
|---|---|
| 「看不出在动」 | `drift = t*0.008` 换算到本卡高 622px 只有 **~5px/s** —— 屏幕上基本等同静止 |
| 「偏疏」 | ① 密度 34（点距 18px）；② **`dotMask *= smoothstep(-0.3,0.6,wave) * 0.6` —— 波谷把点整片杀光**，这才是「显得疏」的主因 |

**改后参数**（全部在 `redesign-preview.html` 的 `FS` 数组内）：

| 项 | 原 | 新 | 理由 |
|---|---|---|---|
| 点阵密度 | `gp*34.0` | **`gp*52.0`** | 点距 18 → **12px** |
| 点径 | `smoothstep(.05,.14)` | **`(.055,.155)`** | 按「格」算 → 密度升时点自动缩，**面积占比几乎不变** |
| drift | `0.008 / 0.005` | **`0.022 / 0.015`**（×2.75） | 卡内 ~5 → **14px/s** |
| **sway（新增）** | — | `vec2(sin(gp.y*12+t*0.55), cos(gp.x*10+t*0.46)) * 0.20` | 见下 |
| wave 相位速度 | `0.15 / 0.12` | **`0.34 / 0.28`**（×2.3） | 周期 42 → 18.5s |
| wave 保留系数 | `0.6`，阈值 `(-0.3,0.6)` | **`0.78`**，阈值 `(-0.55,0.45)` | 暗区只变暗、不消失 |
| 帧率 | 30fps 节流（`MIN_DT`） | **不节流 ≈60fps** | 动效明显后 30fps 有步进顿感 |

### 1. 为什么必须新增 sway（而不是把 drift 调得更快）

只靠 drift，整片点阵是**刚性平移** —— 观感是「背景在滑动」，不是「点在动」。
sway 让每个点**在自己的格内游走**，相位由 `gp` 决定（相邻格差 `12/52 ≈ 0.23rad`）
→ 形成**连续波面扫过**，不是各自乱跳。

⚠️ 关键量级：**肉眼看到「在动」靠的是波面速度 ω/k ≈ 42px/s，不是单点位移速度**（后者只有 ~1px/s，根本看不出来）。
调这类动效时若只盯「点位移多少像素」会误判为「还是没动」。

**可复用几何边界**：点半径 `r` + 合成最大偏移 `amp*√2` 必须 `< 0.5 格`，
否则点会被 `fract` 的格边界切开 → 闪烁。本次 `0.155 + 0.283 = 0.438` ✓（余量 0.75px）。

### 2. 可读性核算（为什么点变密却不伤白字）

点径与点距**等比缩放** → 点面积占比几乎不变（1.6% → 1.9%），平均亮度基本不动。
按全链路 `mix(col,lineColor,dotMask*0.35)` → `screen` → `opacity .42` 算最亮点像素：

| 参数 | 最亮点像素 | 白字对比度 |
|---|---|---|
| 旧（密度 34 / 系数 .60） | RGB(52,97,220) | 5.40 |
| **新（密度 52 / 系数 .78）** | RGB(57,101,221) | **5.15** ✓ AA |
| 蓝底本身 | #1d4fd8 | 6.64 |

**降级路径**：CSS 兜底点阵同步改 `background-size: 12px` + `radial-gradient(... 0.9px, transparent 1.1px)`（原 18px）。

### 3. 自检结果

HTML 配对 ✓ / CSS 233:233 ✓ / JS `node --check` ✓ / GLSL：括号平衡、`sway` 声明早于使用、
内建函数全在 ES 1.00 内、uniform 声明集与 JS 取 location 完全对应 ✓ / 旧数值残留检查全 0 ✓。
