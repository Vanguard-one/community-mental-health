## 排障记录：「登录后进不去页面，被弹回登录页」

**症状**：点登录 → 提示成功 → 立刻整页刷新回 `/login`，且表单被清空（"账号密码都没了"）。

**根因：Redis 没启动。** 后端 `JwtAuthFilter` 里 `redis.hasKey(BLACKLIST_PREFIX + token)`
写在 `try` 内，Redis 连不上抛 `RedisConnectionFailureException` → 被同一个 `catch (Exception e)`
吞掉 → 统一 `write401`。于是：

| 请求 | 带 token | 走到 Redis 吗 | 结果 |
|---|---|---|---|
| `POST /auth/login` | 否 | 否（`hasText(token)` 为 false 直接放行） | ✅ 200，登录成功 |
| 登录后第一个业务请求 | 是 | 是 → 抛异常 → catch | ❌ 401 |

401 触发 `request.ts` 的 401 分支 → 清 `token`/`userInfo` → `window.location.href='/login'`
（F-5，有意保留的整页刷新）→ 表单清空。整条症状链闭合。

**实测证据**：`netstat` 无 6379 监听、无 redis 进程；但 18989（后端）、3306（MySQL）、5173（Vite）均在监听。
登录接口用 `user01/user123` curl 返回 200 且 token 正常签发。

**结论**：这是环境坑，不是代码 bug。**每次起项目必须先起 Redis**，否则表现为"登录成功但立刻被踢"，
极易被误判为鉴权代码有问题。

**代码侧可优化项（未改，待决策）**：把 Redis 黑名单校验与 JWT 解析分开 try，
Redis 不可用时**降级放行**（仅记 warn），而不是一律 401；否则 Redis 单点故障 = 全站无法登录。
更适合按"可用性优先"处理，但会使登出黑名单失效——需要权衡。

## 本轮踩到的坑（都很值钱）

1. **★ 未映射路由被兜底成 `HTTP 200 + body.code=500「系统异常」`**
   `GlobalExceptionHandler` 只有一个 `@ExceptionHandler(Exception.class)`，
   Spring 6.1 的 `NoResourceFoundException` 也落进去。
   → 探测新接口时看到 code 500，一路去核对 SQL 列名 / 字段映射，**浪费了一轮排查**，

- **发现方式**：headless 截图时觉得副标题不对 → `--dump-dom` 拿渲染后真实文本 → 与源码逻辑矛盾 → grep 产物表达式。
  **教训：截图里"小字看着不对"不要靠眼睛判断，dump-dom 一次就定性。**
- **已修**：`isDoctor.value`，并在该行加注释。同文件另外两处（`rules`、`onFinish`）本来就写对了。
- **新增自查脚本**：`.workbuddy/scripts/check_ref_value.py` —— 扫 `<script setup>` 内 `const X = computed/ref(...)`
  后 `X` 未被 `.value` 解引用的位置（排除类型标注、`watch(X, …)` 这类合法整体传 ref）。

## 16:45 诊断「预警工单只显示 user01，别的居民做完问卷不显示」→ 结论：不是 bug

**用户报障**：预警工单只显示 user01 的测评，别的用户做完问卷没进医生端工单。

**排查路径（全部只读）**：
1. 查库：账号 3 个居民——`user001`(id5)、`user01`(id6)、`user02`(id7)；
   测评 3 条、工单 1 条。
2. 逐条对照测评与工单 → 见下表，**完全自洽**。
3. `GET /alert/8/assessment` → `residentId=7, residentName='张*', assessmentId=9`，
   逐题 9 题齐全、history 2 条 —— **无串数据**。
4. 截图医生端 `/admin/alerts` → 显示的就是「居民 #7 的危机工单」，**不存在"只显示 user01"**。
5. `AssessmentService.java:130` → `alertEngine.evaluate(assessment)` **无条件调用**（不在任何 if 内）。
   → 排除了"某些居民提交时不触发引擎"的可能。

**根因：预警工单不是"答题流水"，只有三种条件才建单**（`AlertEngine.evaluate`）：

| 类型 | 条件 |
|---|---|
| CRISIS | `crisis_flag = 1`（任一危机项阳性）→ 强制 D 级 |
| THRESHOLD | `risk_level ≥ B` **且** 非危机 |
| TREND | 相邻两次测评总分**涨 ≥ 5 分**（`trend-window-days: 90` 窗口内，较上一条） |

用户实测 3 条测评的判定：

| 测评 | 居民 | 总分 | 风险 | 危机 | 判定 |
|---|---|---|---|---|---|
| #9 | user02 | 7 | D | **1** | ✅ 建工单 #8（CRISIS） |
| #10 | user02 | 0 | A | 0 | ❌ 无危机 + A<B + 比上次(7分)降了 |
| #11 | user01 | 1 | A | 0 | ❌ 无危机 + A<B + 该居民无上一条可比 |

**为什么用户会有「只有 user01」的观感**：清空前那 7 条工单**全部属于 `resident_id=6`（user01）**——
因为当时只有 user01 做测评时触发过规则，别人做的都是低风险卷，三条规则都不沾。
> 关键认知：**「预警工单」是给医生派的任务，不是测评记录列表**。若每次测评都建单，医生端会被低风险问卷淹没。
> 用户若想"看到全部居民的测评"，正确做法是**另加一个测评记录视图**，而不是放宽建单门槛。
