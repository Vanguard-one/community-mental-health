# PsyCare 关键决策与细节（MEMORY.md 的展开卷）

> 主文件 `.workbuddy/memory/MEMORY.md` 只留硬约定/环境坑/资产/待办/文档地图。
> 本文件承载「为什么这么做」的决策记录，避免反复推翻。改动设计前先读这里。

## 一、架构与账号

- 账号模型 = **基表 + 三角色表**（不是三张独立表）：`sys_user` 存 `username/password/role/status/is_deleted`，
  `user`/`doctor`/`admin` 只存**差异字段**，主键 `IdType.INPUT` 沿用 `sys_user.id`。
  零冗余、无双写；账号状态/开关/软删一律落 `sys_user`（角色表是附属表）。
- 跨角色引用依赖 **id 全局唯一**：`notification.user_id`、`alert_record.handler_id` **不带角色字段**。
  任何「把 sys_user 拆成多张独立表」的方案必须先解决 id 全局性与 username 跨表唯一性。
- 软删 + 唯一索引 = MySQL 8 函数索引 `UNIQUE ((IF(is_deleted = 0, username, NULL)))`：
  已删行表达式为 NULL，唯一索引不约束 NULL → 软删后同名可重新注册。
- 软删真生效须**三处齐做**：DB 真建 `is_deleted` 列 + 实体加 `@TableLogic` + yml 改 `logic-delete-field: isDeleted`。
  **只改 yml 而不建列 = 静默失效，`removeById` 仍是物理删除。**
  > 早期「`logic-delete-field: deleted` 是误报、不要修」的结论已被角色拆分需求推翻——那条判断只在「它无害」时成立。
- `resident_profile` 是**死表**（实测 0 行）：`AuthService.register` 只写 `sys_user`，从不写 profile；
  `DataInitializer` 只给医生建档案。设计任何「居民扩展字段」功能前先确认。
- `assessment` + `assessment_answer` 已存在且与工单直连（`alert_record.assessment_id`）。
  需求若说"新建做题记录表"，先核对——很可能只需补查询接口。

## 二、前端与路由

- 登录页**不预选身份**，注册入口只有一个 → `/register`（**不带 `?type=`**）。
  居民/医生身份切换在**注册页内部**（`type-switch`）——不要搬回登录页，也不要删掉，删了医生就没法注册。
- 登录落地页：ADMIN→`/admin/dashboard`、DOCTOR→`/admin/alerts`、RESIDENT→`/home`。
  `Login.redirectByRole` 必须与 `AdminLayout.homePath` 一致。
- 工单处置台是**单页左右分栏**，`/admin/alerts` 与 `/admin/alerts/:id` 共用同一组件（主从结构，不是两个页面）。
- `/history`、`/notifications` 是设计稿外页面，按 `tokens.css` 自行延展，不要等设计稿。
- **居民端「找医生」现在是两个页面，别再当成一个**（Phase 2.5）：
  `/doctors` = 「**医生咨询**」（顶部菜单，**科室分类** → 点科室看医生列表 → 咨询），
  `/ai-recommend` = **AI 推荐结果**（`?sessionId=N`，AI 应允后跳来，卡片带「立即咨询」）。
  原来的 `DoctorRecommend.vue` 已删除，两页都能**原地开聊天抽屉**（不再跳去菜单找第二遍）。
- 响应式**只保证 ≥1280 桌面端**，不做移动端。F-5 有意保留：401 用 `window.location.href='/login'` 整页刷新。
- 静态检查抓不到的两个坑：
  ① `v-for` 与 `v-else` **不能挂同一元素** → 用 `<template v-else>` 包一层，只有编译会报；
  ② 数组字面量里只有某项带可选属性 → 推断成联合类型，`i.xxx` 报「属性不存在」→ **每项都显式写满该属性**。

## 三、数据与业务规则

- **工单状态机有一条「只有管理员能走」的恢复边**：`REJECTED / CLOSED → PENDING`（`AlertService.reopen`）。
  它**故意不进 `TRANSITIONS` 流转表**，走独立接口 `POST /alert/{id}/reopen`（仅 ADMIN）：
  从终结态回到待确认是管理员的**越权恢复**动作，不是业务流转的一环；写进流转表医生端也会顺手用上。
  三条细节：① 目标状态固定 `PENDING`，不接受前端传 `toStatus`（不恢复成终结前的 `FOLLOWED`——
  那样医生只能「结案」，等于没给重新核实的空间）；② 清空 `handler_id` + `handle_note`（保留会显示
  「待确认 + 处理人 #2」的自相矛盾态），原备注仍留在流转日志里；③ 必须写一条流转日志，否则工单「无痕复活」。
  前端只在 `role === 'ADMIN'` 时渲染入口，医生端处置面板原样保留「该工单已终结」提示。
  重开后**前端重新拉列表**（工单会从「已办结」跳到「待确认」，只改本行会留下幽灵行），但右栏不重选。
- **删数据前扫列名，不要只查外键**：本项目**没建任何外键约束**，
  `information_schema.KEY_COLUMN_USAGE` 查 `REFERENCED_TABLE_NAME` 永远返回空。
  要扫 `information_schema.COLUMNS` 的 `COLUMN_NAME LIKE '%xxx%'`，再逐表数「非空行数」确认是否真被引用。
- `consult_session` 两列引用**一空一实，结论不可互推**：`alert_id` 27 行全 NULL（死列），
  `assessment_id` 有 6 行真实数据（居民做完测评从结果页发起的 AI 问诊）。
  → 删 `assessment` 必须把 `consult_session.assessment_id` **置 NULL 断开**。
  连带删法：`alert_status_log` 跟工单删、`assessment_answer` 跟测评删、
  `consult_session` 是独立业务（问诊），**只断引用不删行**。
- **工单只有三种建单条件**（`AlertEngine.evaluate`，`AssessmentService:130` 无条件调用）：
  ① `crisis_flag=1`→CRISIS/D；② `risk_level≥B` 且非危机→THRESHOLD；③ 相邻两次总分涨 ≥5（90 天窗口）→TREND。
  **低风险卷（A 级、无危机、分数未涨）不产生任何工单，这是设计不是 bug。**
  用户曾据「工单里只有 user01」误判为故障，真因是别人做的都是低风险卷。
  若需求是"医生端看到全部居民测评"，正确解法是**新增测评记录视图**，别放宽建单门槛。
- `AlertEngine.createIfAbsent` 幂等条件是「**同类型 PENDING 才跳过**」，不是「同类型已存在就跳过」。
  → 工单全部处置完（非 PENDING）后清空数据，下次做测评会**照常重新出单**。
- `assessment_answer.item_no`/`score` 实测 68 行全为 NULL（写入侧从未赋值）。
  查询用 `scale_item.item_no` 与 `COALESCE(aa.score, so.score)`；`submit()` 已补写这两列作为冗余快照。
- 工单右栏「评测做题记录」**按筛查表（量表）分组折叠**，组头右侧下拉箭头展开，
  **不再有「历史测评」列表**（2026-09-28 用户明确要求删掉那个区块）。两个坑：
  ① 分组数据**以 `history` 为准、`record` 兜底并集**（两者可能不重合，只信 `record` 会漏看当前答卷）；
  ② `history` **只有摘要，没有 `answers` 也没有 `crisisFlag`**，逐题明细要逐条调 `GET /assessment/{id}`——
  实现上是**展开某组时才并行拉该组**并入 `answerCache`，**进页面不拉全量**。
- MyBatis 五表 join 的扁平结果**必须用 `<result>` 而非 `<id>`**：一行 = 一题，
  用 `<id>` 映射 `assessmentId` 会把同 id 多行**去重合并**，逐题明细只剩最后一题。
- `@Builder` 与 MyBatis 冲突：生成的全参构造器吃掉无参构造器 → MyBatis 无法实例化。映射用 VO 必须 `@Data`。
- `GlobalExceptionHandler` 曾把契约错误说成系统故障（404/405/坏 JSON/缺参全落进 `Exception` 兜底，
  返回「系统异常」并把 404 记成 ERROR 堆栈）。已拆出 4 个专用处理器。
  **别再加 `@ExceptionHandler(Exception.class)` 之外的粗粒度兜底。**

## 四、医患聊天（Phase 8 / 8.1 / 8.3 + 2026-09-29 收敛到专有页）

- **零建表**：复用 `consult_session` / `consult_message` + `consult_type='DOCTOR'`
  （两表注释原文就写着「电话/医生图文/AI 三种渠道统一」，`ConsultType` 也早留了 `DOCTOR`）。
  三条不可松的口子：
  ① 发送者身份**只从 JWT 推导**，绝不接受前端传 `sender`/`senderId`；
  ② 每个读写入口必须 `requireMember` 校验会话归属（**会话 id 自增，不校验就能改 URL 遍历他人聊天记录**）；
  ③ 脱敏按视角分裂——医生看居民脱敏（患者隐私）、居民看医生**不**脱敏（服务提供者，推荐页本就展示真名）。
  会话**复用而非每次新建**（`resident+doctor+DOCTOR+OPEN` 唯一），否则点十次「聊天」就有十条空会话。
- **「未读」用消息方向代替 `read_flag`**：`consult_message` 没有已读列，加列要走 DDL。
  `awaitingMyReply = (最近一条消息来自对端)` → 零 DDL，且语义更准（点开但不回，仍该提醒）。
  医生端侧栏角标 = 待回复会话数。**不要为「未读红点」去加 `read_flag` 列。**
- 医生端两入口分工固定：「用户信息」= 主动找人（扫患者档案、顺手点聊天）、
  「消息列表」= 被动接收（谁发了消息、谁还没回）。两者共用 `ChatPanel`，同一会话从哪进都是同一份记录。
  **不要合并成一个页，也不要让任一边分叉出自己的聊天实现。**
- **居民可主动发起会话**（Phase 8.1 起，此前「只能医生先发」的边界已作废）。
  `GET /chat/doctors` 必须**四重过滤**：`is_deleted = 0` + `status = 1` + `doctor.audit_status = 'APPROVED'`
  + **「有过消息」**（Phase 8.3 加）。漏前三重任一条，会让「连登录都进不来」的医生出现在居民端可选列表里。
- **「有过消息」= 该会话下至少 1 条 `consult_message`**（Phase 8.3，两端同一口径）。
  四个「不看」：不看方向（若要求双向，刚发消息对方没回时两端列表会同时消失，自相矛盾）、
  不看条数、不看会话状态（CLOSED 的历史消息仍算往来过）、不看已读。
  实现是 SQL 层 `EXISTS` 半连接，**`selectDoctorList` 里的 EXISTS 要写两处**：
  子查询那处决定「取哪条会话」——不写会在最新会话恰好为空时挑中它、跳过更早有消息的那条；
  外层 `cs.id IS NOT NULL` 决定「这行留不留」。别只写外层就以为过滤干净了。
  过滤**必须下沉到 SQL**：会话列表 / `messageCount` / 侧栏待回复角标共用同一结果集，口径要在源头统一。
  `/chat/sessions/{id}` 详情**有意不过滤**——刚建的空会话得能打开、能发第一条消息。
  空会话只是不显示，不是被删；对方发出第一条消息它立刻回到列表顶部。
- **✅ 居民端「开新对话」入口缺失 —— 已于 Phase 2.5 补齐**：
  `/chat/doctors` 过滤掉空会话后，全新居民的「我的消息」恒为空、无从发起第一句话。
  修法**没有放开过滤**（那会让侧栏把全院医生列一遍），而是新增
  `GET /chat/doctor-catalog`（**不过滤**「聊过的人」条件）+ 两个新页面：
  「医生咨询」`/doctors`（科室分类 → 科室医生列表 → 「咨询」按钮）与
  AI 推荐结果页 `/ai-recommend`（「立即咨询」按钮）。两个接口并存是刻意的：
  「聊过的人」（`/chat/doctors`，给侧栏）vs「能聊的人」（`/chat/doctor-catalog`，给找人页）。
- `/chat/**` **只放行 DOCTOR 与 RESIDENT**，管理员不在医患链路上（菜单也不给）。
  因此 `AdminLayout` 的角标**不能合并成一个请求**：待审核数走 ADMIN-only 接口、待回复数走 `/chat/sessions`。
  菜单角标文案走菜单项的 `badgeTip` 字段（原先模板里硬编码「N 位医生待审核」，加第二个角标就露馅）。
- 会话列表排序**由 SQL 一次给定**（医生端 `COALESCE(lastMessageAt, cs.created_at) DESC, cs.id DESC`、
  居民端 `lastMessageAt DESC, d.rating DESC`）。前端不二次排序——「最近联系人置顶」的语义只存一份，
  否则两处迟早打架。Phase 8.3 后原排序键 `cs.id IS NULL` 恒 false，已删。

### 4.1 聊天界面收敛到专有页（2026-09-29）

**背景**：居民端曾有**三个**开聊入口 —— 医生咨询页、AI 推荐结果页、我的消息页 ——
每处都自己写了一遍「手写遮罩 + 420px 抽屉 + `ChatPanel`」。三套 DOM、三套样式，
抽屉标题栏的信息还各不相同。抽屉这个形态本身是从「推荐页顺手一开」长出来的，
当它变成三个页面的共同出口时，"顺手"就不再成立了。

**定稿**：一律 `router.push('/messages/:doctorId')`，聊天只有一个容器。

| 项 | 决定 | 理由 |
|---|---|---|
| 路由参数 | `doctorId`（不是 `sessionId`） | 从「医生咨询」进来时会话**还不存在**，URL 里只可能带 doctorId。用 sessionId 就必须跳转前先请求一次 → 多一次往返 + 「查到的会话已过期」的竞态 |
| 会话建立时机 | **目标页**调幂等的 `POST /chat/sessions` | 入口页预建会话，会在「点了但没进去」时留下空会话；它不显示在列表里（SQL 有 `EXISTS` 过滤），所以只会慢慢积累而无人发现 |
| 标题栏数据 | 复用会话接口，**顺带**下发医生资料 | `sessionJoins` 早就 `LEFT JOIN doctor d`（为取 `d.title`），补三列零成本；否则聊天页要为三个静态字段再调一次带三个聚合子查询的 `/chat/doctor-catalog` |
| 页面尺寸 | `max-width: 940px` 居中卡片，高 `calc(100vh - var(--header-h))` | 更宽会让一句话横跨半屏；更窄则正常长度的话折三行。整页不滚动、只有消息区滚动，输入框永远贴底 |
| 安全提示 | 标题栏下方常驻一行（12356 / 120） | **静态声明，不做任何自动判定** —— 所以不会误伤正常对话（与 Fix-1 的教训一致：能自动拦的东西越少越稳） |
| 医生端 | 不动（仍是左右分栏 + 抽屉） | 那边是「医生与用户聊天」，主从结构里抽屉是合理的；且医生端的列表是**常驻**的（要看到谁还没回），跳页会打断这个流程 |

**「聊过就出现在我的消息里」不需要回写**：判定条件是「该会话下至少 1 条 `consult_message`」，
落在后端 SQL，两个列表共用同一条链路。所以副作用是**有意的**：进页面看一眼不说话，
不会在列表里留下空条目。

**`ChatPanel` 的增强对所有使用方生效**（两侧头像、日期分隔条、友好空态、`canSend`）。
它的契约没变（仍是「填满父容器」），所以医生端两个入口自动受益 —— 这是共用组件该有的样子，
也是当初「不抽公共抽屉、却抽公共面板」这个划分的回报：**面板是能力，外壳是布局**。

> [!note] 头像在窄容器里要让位
> 医生端抽屉只有 420px，加上 32px 头像 + 间距，气泡就窄了。
> 用 `@container (max-width: 440px)` 隐藏头像，而不是 `@media` —— 后者看的是视口，
> 抽屉在 1280px 视口下也不会触发。`ChatPanel` 因此加了 `container-type: inline-size`。

## 五、AI 助手模块（2026-09-29 选型定稿）

完整计划见 `AI助手开发计划.md`（1156 行）。这里只记**为什么这么定**与**不能忘的事实**。

**三条已核实的事实（当日实查，非记忆）**：

1. **DeepSeek 没有 embedding 接口** —— 官方只有 `deepseek-v4-flash` / `deepseek-v4-pro` /
   `deepseek-v4-flash-vision-exp`。所以 RAG 必须是「DeepSeek 生成 + 第二家向量化」两段式。
   `EmbeddingClient` 从第一天就得是接口 + 配置选实现，否则换模型要改业务。
2. **`deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 退役**，调用直接失败无回退。
   项目 `application.yml` 配的正是 `deepseek-chat` —— 即**当前 AI 对话在改配置前就调不通**。
3. **Milvus 2.6 向量字段不可为 NULL**（`nullable vector` 到 2.6.18 才有）。
   这直接导致「父块不进 Milvus、只留 MySQL」，而这条恰好也是更正确的分层。

**核心架构判断**：

- **MySQL 是事实源，Milvus 是可重建索引层。** 所以**先写 MySQL 再写 Milvus**，
  Milvus 失败仅告警不阻断（rebuild 能补）。这句话决定了双写的顺序与验收方式。
- **Milvus 2.6 自带 BM25**（`Function type=BM25` + `SPARSE_INVERTED_INDEX` + `RRFRanker`），
  混合检索不需要外部稀疏向量接口 —— 正好补上 DeepSeek 缺 embedding 的短板。
- **提示词按稳定性分层**（人格/边界/输出/流程 → 档案摘要 → 检索 → 历史 → 输入），
  L1–L4 严禁出现时间戳或 id：DeepSeek 的自动上下文缓存靠前缀字节级一致，写进去就 100% 不命中，
  而且**不报错，只在账单上体现**。
- **阶段推进用「规则裁决 + LLM 建议」**，不让 LLM 单独定阶段（不可测、可被 prompt 诱导）。
  与「工具入参的 `userId` 必须服务端注入」是同一个安全思路。
- **合成语料只能验链路**：Recall@5 用它测是有效的（测的是检索能力，与内容正确性无关），
  但**医学正确性无法用它验证**。全链路 `source_type='SYNTHETIC'` 标记 + 前端角标 + 上线前整体替换。

**已核实的技术坑**：

| 坑 | 后果 | 出处 |
|---|---|---|
| BM25 那一路必须 `new EmbeddedText(text)`，不能 `FloatVec` | `ParamException: Search target vector type is illegal` | 官方 issue #1402 |
| **中文 BM25 必须配分词器**，默认按空格切 → 整句成一个 token | 中文检索召回几乎必然为 0 | 需探针实测确认 |
| collection 必须 `loadCollection` 后才能 search，写完立刻查要 `flush` | 表现为"写进去了却检索不到" | 官方文档 |
| COSINE 索引 ↔ COSINE 查询，索引与查询度量必须一致 | 用 L2 索引发 COSINE 直接报错 | dbVisitor 文档 |
| Java SDK 版本要与服务对齐：Milvus 2.6.x ↔ `milvus-sdk-java` **2.6.22** | 版本不齐可能缺 hybridSearch | 官方 release 表 |
| SDK 自 v2.5.2 拆包，只需 `milvus-sdk-java`，不需 `-bulkwriter` | 多引一个没用的包 | 同上 |
| Reactor 没有 `timeout(首信号, 后续信号)` 双参数重载（那是 RxJava） | 按错误写法写会编译不过或用错语义 | 本次修正，原设计文档表述有误 |
| `SignalType` 的取消信号：reactor-core **3.6.0 是 `CANCEL`**，3.7+ 才是 `ON_CANCEL` | 写 `case ON_CANCEL ->` 编译报「枚举 switch case 标签必须为枚举常量的非限定名称」——**措辞误导**，看着像 Java 语法写错 | 本次踩到，`javap -cp <jar> reactor.core.publisher.SignalType` 一眼确认 |

正确写法是两行组合（`timeout(Duration)` 的语义就是**元素间**超时，天然覆盖首 token）：

```java
upstream.timeout(Duration.ofSeconds(firstTokenSeconds))  // 15s 没吐第一个字 → 立刻降级
        .take(Duration.ofSeconds(timeoutSeconds));       // 整体 60s 上限，到点截断
```

### 5.2 Phase 1 实现决策（2026-09-29 已完成）

代码级记录、实测三事实与验收见 `开发文档.md` 第十三章；契约见 `SSE事件协议.md`。
这里只留**权衡**：

- **泛化一个 `OpenAiCompatClient`，而不是每个供应商一个类。**
  原 `DeepSeekClient` 里没有一行 DeepSeek 专有逻辑。**共性收进一个类，差异收进配置**
  （base-url / path / model / effort），否则 QwenClient / GlmClient 会是几个 99% 相同的类。
- **`base-url` 到版本段为止，`path` 从版本段之后开始。** 这是本项目与供应商无关的硬约定。
  双拼版本段（`/v1/compatible-mode/v1/...`）只报 404，看不出真因 —— 所以写进配置注释，
  而不是指望下次记得。`models-path` 留空时由 `path` 推导，少一个配置项。
- **启动探活只调 `/models`，不调对话接口。** 「Key 有效 / 模型名存在」一个 GET 就够了，
  用**会计费**的接口验最便宜的属性是反的。探活失败**只打 ERROR 不阻止启动**：
  AI 只是一个模块，Key 缺失时其余功能应照常可用。
- **累计缓冲区接在「下发给前端的事件」上。** 接上游 chunk 的话，降级话术与兜底文案不入库，
  「库里存的」≠「用户看到的」，事后审计会读到一段从未发生过的对话。
  接事件是白拿的一致性。
- **输出侧危机替换必须配 `override` 事件。** 词表含「自杀」，而 system prompt 明确要求
  模型建议拨热线 —— 合规回答必命中替换，而那段原文**已经流到浏览器了**。
  不发 override，DB 与用户所见就不一致，这是合规问题不是显示问题。
- **`LLM_NO_CONTENT` 与 `LLM_TIMEOUT` 分开、降级话术拆两条。**
  「模型没组织出回答」与「服务连不上」成因不同，都报「服务不可用」是误报，
  用户会白等一次重试。
- **`reasoning_tokens` / `cached_tokens` 各占一列。** 前者是推理模型的隐性开销（按输出价计费），
  后者单价约为未命中的 1/10。合成一列 = 把「前缀是否稳定」这个唯一可量化的降本指标抹平。
- **`temperature` 默认不发。** 未经验证的采样偏好不固化进配置；要用评测集先跑出稳定性基线。
- **DDL 先在 `psycare_ddl_check` 空库演练再上真库**（`run_sql_file.py --db`）。
  建表类脚本风险低，但约定就是约定，且演练成本只有一条命令。

### 5.3 密钥配置：直写 yml，不用占位符（2026-09-29）

**决策**：`api-key` 直接写真值在 `application.yml`，删掉 `${LLM_API_KEY:}`。

**当时的取舍**。占位符方案在教科书上是「正确答案」，但它的失效模式很贵：
忘配环境变量时，占位符会被当成真密钥发出去 —— 应用**正常启动**、日志**干净**、
页面能开、所有接口返回 200，直到第一位用户在聊天框发消息，才看到 AI 不回话。
这条链路上没有任何一个环节会报错。而本地开发「clone 下来就能跑」的价值是即时的。

**可覆盖性没有丢**。Spring Boot 的宽松绑定让下面三种方式优先级都高于 yml，
**且不需要在 yml 里写 `${}` 来「接收」**（这点容易误解，写成 `${VAR:}` 反而把 yml 变成了必填项）：

```
PSYCARE_LLM_API_KEY=sk-xxx              # 环境变量
-DPSYCARE_LLM_API_KEY=sk-xxx            # JVM 参数
--psycare.llm.api-key=sk-xxx            # 启动参数
```

所以生产要「密钥不进镜像」时，改一行占位符或直接靠环境变量注入即可，本地不受影响。
若本仓库日后推送公开远程，第一件事是把 yml 里这行换成占位符。

**顺带补掉的三个坑**（写进 `LlmProperties`，都不报错、只表现为 401 或日志泄漏）：

| 坑 | 失败表现 | 处理 |
|---|---|---|
| yml 引号保留尾随空格 | `Bearer sk-xxx ` → 401「鉴权失败」，肉眼辨不出差一个空格 | `resolvedApiKey()` 统一 trim，全项目只用它读 key |
| 占位符没换 | 与「密钥真的被吊销」同样报 401，但下一步动作完全不同 | `isPlaceholderKey()` 识别 `sk-xxxx`/`your-key`/`changeme`/`<...>`，探活分开报 |
| `@Data` 的 `toString()` | 一句 `log.info("{}", props)` 就把明文密钥写进日志文件 | `apiKey` 加 `@ToString.Exclude`；需要辨识时打 `maskedKey()` = `sk-347***dd66` |

### 5.4 Phase 2：引导问诊与历史入口的权衡（2026-09-29）

代码级记录与验收见 `开发文档.md` 第十四章。这里只留**权衡**。

- **阶段机做成纯函数（`StageRules.advance`），在线推进与丢失重建共用它。**
  这是这一阶段唯一「不做就会长期痛」的决定。Redis 里的阶段随时可能丢（TTL 2h / 重启），
  重建的唯一依据是历史消息重放。若重放走另一份判定逻辑，它与在线推进的差异**不会报错**，
  只表现为「偶尔跳到别的阶段」—— 而它只在 Redis 冷启动时出现，等于一个无法复现的 bug。
  代价是 `StageRules` 只接收字符串输入、不查库，词表必须自带（这也是它唯一变脏的地方）。
- **⚠️ 顺序：先 `load` 再落库本轮消息。** 重放把库里已有消息全算进去；
  顺序反了就是「重放推进一次 + 调用方再推进一次」= **推进两次**，
  且**只在有状态丢失时出现**，有 Redis 时一切正常。已写进 `StageStore` 类注释。
- **`turnsInStage` 与 `turns` 分开。** 只用总轮数做阈值，阶段会一路冲到结尾，
  五阶段退化成「5 轮后给小结」。`decide` 每轮最多进一级，防止一轮连跳两阶段。
- **不引入 tokenizer，用估算函数。** 预算是**安全上限不是账单**，估偏 20% 无影响；
  换一个依赖 + 一份启动开销 + 一处版本兼容问题不划算。CJK 1 字≈1 token，其他 4 字符≈1 token。
- **阶段信息塞进 `meta`，不新开 `stage` 事件。** 阶段在请求**开始前**就定了，
  属「本轮元信息」。每多一种事件类型，两端就多一处必须同步的契约；
  只有「流到一半才出现」的信息才值得独立事件（如 `override`）。
- **取消计划里的「规则 / LLM 双确认」。** LLM 判定阶段要**额外一次调用**，
  每次对话成本翻倍，而规则侧已能在 5 轮内走完五阶段。留了 `StageRules` 作为单一改造点。
- **会话列表接口故意不返回 `stage`。** 列表要显示阶段就得为每条会话各查一次 Redis /
  各重放一次历史，30 条列表变 30 次额外计算 —— 而列表只需回答「何时聊过、几条、最后一句」。
  阶段给明细接口（那里**必须**有，否则切历史会话时指示条会停在「建立联结」直到再发一条）。
- **删除 `PromptBuilder`。** 常量归 `PromptAssets`、组装归 `ContextAssembler`；
  留着就是两套提示词逻辑，必然漂移。注意组装时没有测评要传 `null` 而非 `RiskLevel.A` ——
  传 `A` 会伪造出「系统评估风险等级为 A」这句假信息进 prompt。
- **`crisisStream` 也推进阶段。** 危机短路不调模型，但用户确实说了一句话；
  不推进的话危机之后的阶段会停在原地。
- **单条超长在服务端截断**（`single-message-max-chars: 1000`）。前端 `maxlength`
  只是「不给输入框」，粘贴与接口直调都绕得过。
- **摘要用独立单线程池，不用 `ForkJoinPool.commonPool()`。** 摘要是一次阻塞 HTTP 调用，
  占公共池会影响并行流；池配 `ArrayBlockingQueue(64)` + `DiscardOldestPolicy`，丢了也不影响对话。
  摘要落库必须用 `LambdaUpdateWrapper.set("summary", ...)` **只更新 summary 列** ——
  `updateById` 会写回整实体，把已 CLOSED 的会话改回 OPEN。
- **历史消息按 `id` 升序而非 `created_at`。** 同秒落库的两条时间戳相同，排序不稳定，
  会出现 AI 回复排在用户提问之前。

### 5.5 `FIELD_WORDS` 词表只能靠真实语料回归

自检里抓到：`FIELD_WORDS` 的「时长」组只收了「几个月」，**漏了「个月」** ——
「大概两个月了」抽不到 `duration`，主诉阶段判定信息不足，阶段推进比预期慢。
这类漏词**不报错**，只表现为「AI 怎么老在一个阶段打转」，从日志上完全看不出。

结论：词表属于**语料驱动**的资产，改它必须拿真实对话回归（跑 `Phase2Check` 那套断言骨架），
不能凭想。将来接上真实数据后，应该把「未命中任何关键词的输入」记下来反哺词表。

### 5.6 危机判据：为什么输入侧与输出侧必须口径相反（2026-09-29，Fix-1）

代码级记录见 `开发文档.md` 第十五章。这里只留**权衡**。

- **同一个词表，两侧的判据方向相反。** 输入侧判「居民说了什么」，宁可误报 ——
  多提示一次热线只多一句废话，漏一次可能是一条命。输出侧判「模型写了什么」，
  宁可漏报 —— 真正要拦的是**可操作的自伤指引与教唆**（方法、步骤、剂量），
  而不是「提到自杀这个词」。这两件事形状相似、目标相反，共用一个 `hit()` 必然出错。
- **事故的形状值得记住**：prompt 的 L2 第 3 条**要求**模型在风险语境下建议拨打 12356。
  于是「模型说了 12356」是系统**想要**的结果，而它同时又是「危机」的标志 ——
  用一个业务上鼓励出现的内容当异常信号，是把正常判成异常的标准配方。
  同类错误在本项目还有第二例：前端 `CRISIS_MARK = '12356'` 子串判断。
  两者症状完全一样（气泡变红 + 弹出「已为你转接人工」），所以只修一处不够。
- **输出侧的操作性词表不能收疑问副词。** 「怎么 / 如何」与「你怎么会有这种念头」
  这类共情问句高频共现，收进去会立刻把误报率打回去。只收能构成「教方法」的词。
- **危机与否交给服务端说，前端不反推。** 为此新增了 `crisis` 事件。
  这与「每多一种事件类型就多一处契约」的克制原则冲突，但这次值得：
  替代方案是前端维护关键词启发式，而**它已经证明会出错**。
  判断依据应该在唯一知情的那一侧。
- **`INPUT` 与 `OUTPUT` 的文案必须分叉。** 输入侧真建 CRISIS 工单，可以承诺「已转接人工」；
  输出侧不建 —— 凭模型一次失言就给居民贴危机标签是另一种伤害。
  没有工单却承诺转接，就是一句不会兑现的话：**在心理场景里，这比不承诺更伤人。**
  前端为此加了 `transferPromised`，历史会话用「居民消息 `crisisFlag=1`」反推 `INPUT`
  （这是可靠的：输入侧短路会给居民消息也打上 1，正常路径恒为 0），判不出来就按「不承诺」渲染。

**同批修掉的 `StageStore` 序列化缺陷，教训更普适**：裸 `new ObjectMapper()` 不认
`LocalDateTime`，异常被 warn 吞掉，而重放兜底路径让功能**看起来完全正常** ——
所以这个 bug 只体现在「日志每轮一条重放、`回看=N条` 从 0 逐轮 +1」上。
**「吞异常 + 有等价兜底」是静默失效的完美配方**；要留一条能被人核对到的痕迹。

### 5.7 Phase 2.5：问诊提效与推荐闭环的权衡（2026-09-29）

代码级记录与验收见 `开发文档.md` 第十六章。这里只留**权衡**与**踩到的坑**。

- **编号：这是 2.5，不是 3。** 计划文档里 Phase 3 = RAG 离线管道。本轮是 Phase 2 交付后的
  试用反馈修正（缩短轮次 + 推荐闭环），与 RAG 无交集，记作 2.5 **不挤占 3–6 的编号**。
  曾经把它写成「Phase 3」散在 5 处，后来全改回来 ——
  **跨文档给新工作起 `Phase N` 之前先去源头核对编号有没有被占用**，编号错会让后来人按错的里程碑排期。
- **阶段从 5 段压到 3 段，删掉的两段是「下沉」不是「砍功能」。**
  `FUNCTION_IMPACT`（睡眠/工作受影响）本来就是主诉澄清的组成部分，单独立一个阶段只是把一段话拆成两轮；
  `RISK_SCREENING` 并入**安全边界** —— 危机识别由 `CrisisDetector` 全程兜底，与阶段无关，
  **而靠问一句并不能提高召回，却让每个用户都被问一次**。
- **⚠️ 本轮唯一的真实缺陷：阈值与时序耦合。** 推进发生在「用户发言之后、组装提示词之前」，
  所以「用户第 N 条之后的阶段」＝「模型第 N 次回复所处的阶段」。`OPENING` 阈值写 `>= 1`
  会让模型**第一次回复就直接落在主诉澄清**，`OPENING`（共情、确认来意）永远轮不到一次回复，
  三个阶段里有一段空转。**不报错、不崩、只是少一句共情，只有断言抓得到。**
  最终 `OPENING → turnsInStage >= 2`；`CHIEF_COMPLAINT → (key >= 3 || turnsInStage >= 2)`，合计 2~3 问即转介。
- **`KEY_FIELDS` 合并后阈值仍是 3，但语义变宽**（睡眠、社交也算关键字段），
  于是「说得多的用户」更快攒够 —— 这正是要的方向。`MAX_QUESTIONS = 3` 单独提常量，
  让「最多问几个」只有一个出处，不散在 `switch` 分支里。
- **应允判定必须「一问一答」，且否定优先。** 前端只看得到后半 ——
  **任何一轮的「好的」都长得像应允**（可能只是在回答「最近睡得怎么样」），
  而「AI 上一轮问过没有」要回看上一轮 AI 回复原文，只有服务端能做到。
  否定优先是中文特有的坑：否定与肯定**共享字形**（「不用」含「用」、「不要」含「要」、
  「不好」含「好」、「不行」含「行」、「不对」含「对」），不先判否定，
  「不用了谢谢」会被读成应允 → 动画弹出、会话被关，用户一脸茫然。
- **`ASK_MARK` 是与提示词的逐字契约。** `ReferralRules.ASK_MARK = "需要我为你推荐合适的医生吗"`
  必须与 `PromptAssets.INTERVIEW_FLOW` 第 3 阶段的固定收尾问句**一字不差**，
  改一处必须同步另一处，否则判定**静默失效**（不报错，只是永远不触发）。
  判定本身写宽松（`推荐 && 医生 && (吗|？|?)`）以容忍模型改写，但**疑问句检查不是可选项** ——
  否则「医生可能会推荐……」这类陈述句会命中。
- **轮次下限 `REFERRAL_MIN_TURNS = 2`。** 第一句就说「我想找医生」不该立刻跳走：
  他还没说任何情况，AI 也还没回应过，直接弹动画会显得 AI 完全没在听。
- **`recommend` 与 `crisis(OUTPUT)` / `override` 互斥。** 不是洁癖：
  **模型刚被护栏拦下时顺势推进推荐流程 ＝ 用正常流程掩盖一次安全事件。** 回复为空也不发。
- **前端「动作信号只记标记」。** `onRecommend` 只写 store 标记，动画/关会话/跳转放
  `chat.send()` 返回之后。回调里 `await` 会**阻塞后续 SSE 帧解析**，遮罩还会盖住**还在流的字** ——
  挪到 `send()` 之后，动画恰好卡在文字流完的那一刻。
- **`/chat/doctors` 与 `/chat/doctor-catalog` 保留两个接口。** 「聊过的人」vs「能聊的人」，
  合并会牺牲一边：过滤 → 新居民看不到任何医生；不过滤 → 侧栏把全院医生列一遍。
  排序 `CASE WHEN cs.id IS NULL THEN 1 ELSE 0 END` 让有对话者排前，
  `LinkedHashMap` 保住分组首次出现顺序。
- **`selectedDept` 放本地 ref，不走 URL query。** 页面只有一个筛选维度，
  不需要可分享/可后退的深链；但 `?dept=` 仍解析，保留直接深链的能力。
- **新 UI 全部手写 CSS + 原生 `button`，零新增 antd 组件**（`vendor-antd` 790.77 kB 未变）。
  动画是双环 `@keyframes orbit` + 3 步渐进点亮，只用了 `Transition`。
  预算只剩约 9 kB，**要加 antd 组件先换掉现有不必要的**（硬约定 #9）。
- **列数不写死。** 指示条 `grid-template-columns` 按 `STAGE_FLOW.length` 内联生成 ——
  写死 `repeat(5, ...)` 在压到 3 段时会把三个点挤在左侧三分之一。阶段数已经变过一次，别踩两次。

### 5.8 会话状态的归属：一个居民一段连续对话（2026-09-29，两版推翻后定稿）

**这一节要连着读 —— 中间推翻过一版，而"被推翻的那版"本身就是个值得记的教训。**

需求侧三次反馈把设计推向了完全不同方向：

| # | 用户原话 | 暴露的问题 |
|---|---|---|
| 1 | 「每次点击 AI 问诊后刷新一下页面，不然容易出现之前结束的会话记录」 | 跳走再回来看到**上一次的消息**（新会话 ID 配旧消息） |
| 2 | 「不太对，每次一刷新就新建会话了，只是刷新一下」 | URL 上的 `assessmentId` 让"从测评页进来之后"的每一次 F5 都新建会话 |
| 3 | 「把历史会话的功能删了…记录一直显示在聊天框就行，也不用刷新了」 | 要的是**根本没有多会话**，而不是"把多会话切得更顺" |

**第 1 版（已废弃）**：判断成"离开页面没清 store"，于是加了
`onUnmounted(() => chat.reset())`，并用「`onUnmounted` 只在 SPA 路由切换时触发、F5 不触发」
论证"刷新恢复不受影响"。
—— **论证本身没错，但方向反了**：用户要的恰恰是"记录一直留着"，
而这个改动把「点菜单进来」变成了"永远新会话"。**一个正确的论证用在了错误的目标上**，
是本节最值得记的一点。

#### 最终设计

| 层 | 做法 |
|---|---|
| 服务端 | `openSession` **幂等**：查最近一条 `status='OPEN'` 的会话复用，并更新 `assessmentId`/`alertId`（只 `set` 非空字段 —— 传 `null` 是"不改变"，见硬约定 #17）。只挑 OPEN：复用 CLOSED 会话会得到"只能看不能发" |
| 前端入口 | `chat.enter(assessmentId)`：带测评 → `open()`（服务端复用并关联）；不带 → `restoreLast()` 恢复最近一段对话，确实没有才新建。拿到 id 后再 `loadSession()` 拉明细 —— `open()` 只保证"会话存在" |
| 数据源 | `restoreLast()` 从**服务端列表**取（按 `id` 倒序第一条），不再用 localStorage。少一个本地状态源，就少一类"本地 id 与服务端对不上"的故障 |
| 生命周期 | **不再关闭会话**。原先 `close()` 是为了"别在历史里留一条没关掉的记录"，历史功能取消后这个理由随之消失；继续关会让用户下次进来只能看不能发 |
| UI | 「历史会话」按钮 + 整个抽屉（模板 / 样式 / `openDrawer` / `onSwitchSession` / `previewOf` / `formatDateTime` / `SESSION_SHOWN`）全删 |

> [!warning] 三条约束，动这块之前先看
> 1. **`AiChat.vue` 不能有 `onUnmounted` 清理**，也不能在任何"离开页面"的时机 `reset()` ——
>    聊天框要一直显示这段对话。store 是全局单例、不随路由销毁，这正是它现在**有用**的性质。
> 2. **代价：登出必须清。** `stores/auth.ts` 的 `logout()` 里有 `useChatStore().reset()`，
>    这是防"换账号看到上一个人倾诉"的唯一防线。删掉不会报错，只会串数据。
> 3. **`Result.vue` 跳转前的 `chat.reset()` 不能删。** 它把 `sessionId` 清成 `null`，
>    否则 `open()` 会因为"已经有会话了"直接返回，**这次测评就关联不上**（右栏的关联测评卡会一直空）。

**为什么"多会话"这个模型一开始看着是对的**：`consult_session` 天生是多行表、`AiSessionVO`
天生是列表，抽屉只是把这份结构忠实地画了出来 —— **是表结构先入为主地定义了产品形态**。
这类情况下，动手做 UI 之前值得先问一句「用户真的需要切换吗」。

### 5.9 演示数据的两个约束：密码只能「搬运」、科室顺序必须显式排（2026-09-29）

**背景**：真库只有 4 位医生 / 3 个科室 / 3 位居民，`/doctors` 页大片留白。
补数据时踩到两件事，都值得记。

#### 一、BCrypt 密码哈希只能从已有账号「搬运」

演示数据要能登录，就得有正确的 BCrypt 哈希；而 BCrypt 不可逆 —— SQL 里**生成不出来**。三条路：

| 做法 | 评价 |
|---|---|
| 硬编码一份现成的哈希字符串 | 能用，但那串哈希对应什么密码从此没人知道；换环境就对不上 |
| 写个 Java 小程序调 `passwordEncoder.encode()` 生成后再拼进 SQL | 多了个必须同步维护的工具，且每次执行生成的哈希都不同，脚本不再幂等 |
| **`SET @pwd = (SELECT password FROM sys_user WHERE username = 'doctor_li' AND is_deleted = 0 LIMIT 1)`** | **选它**：新账号密码与种子账号一致（`doctor123` / `user123`），脚本里不出现任何哈希字面量 |

代价是**执行顺序被耦合**：脚本必须在「后端启动过一次、`DataInitializer` 播过种」之后跑。
这个耦合不是隐患，而是一条明确契约 —— 写进脚本头注释、排查表，报错信息也够直白
（`Column 'password' cannot be null`）。

> 顺带一个 MySQL 细节：`INSERT INTO t SELECT ... FROM t2 LEFT JOIN t ... WHERE t.id IS NULL`
> 是**合法**的（直接 JOIN 目标表，MySQL 会物化）；只有**在子查询里**引用目标表才报 1093
> （`You can't specify target table ... for update in FROM clause`）。
> 一开始写成 `WHERE NOT EXISTS (SELECT 1 FROM t ...)` 正是踩了这个，改成 LEFT JOIN 才通。

#### 二、分组顺序：继承 SQL 的 ORDER BY ＝ 把排序权交给一个无关字段

`doctorCatalog()` 用 `LinkedHashMap` 分组，科室顺序就是「该科室第一位医生在 SQL 结果里的位置」。
而 SQL 的 `ORDER BY` 是「有对话者优先 → 最近消息 → **评分** → id」——
于是**科室顺序实际由「该科室最高评分」决定**。

3 个科室时看不出来；扩到 10 个后实测是
「心理科 → 老年心理科 → 危机干预门诊 → 精神科 → 睡眠医学科 → …」，
既不按人数也不按名称。更麻烦的是它**不稳定**：给某位医生调个评分，整个科室就挪位。

修法是三级显式排序，其中第一条**刻意保留**原设计意图（聊过的科室靠前）：

```
① 组内有进行中会话（sessionId != null）  → 聊过的科室靠前（原意图，保留）
② 医生数降序                              → 人多的信息量大
③ 科室名升序                              → 兜底，让顺序完全确定
```

②③ 与业务无关，纯粹为了「可预期、可复现」。
同类的坑还有 #46（阶段指示条列数不写死）—— **凡是「顺序由数据隐式决定」的地方，
都要多问一句：这个顺序稳定吗？**

#### 三、另一个小教训

写一次性脚本前先 `ls .workbuddy/scripts/`：`run_sql_file.py` 早就在那儿了（见 #54）。

### 5.10 Phase 3 前半：RAG 地基的四个取舍（2026-10-08）

**背景**：`milvus_probe.py` 停在断言 1（本机 Docker 未启动），按计划 5.5.3「不过则停止后续开发」，
Milvus 侧零代码。但另两条外部依赖（通义 Key、模型名）已就绪，且下面两块**不依赖 Milvus 运行**。

**① 为什么可以不等 Milvus 就先做 DDL + `EmbeddingClient`**
门槛针对的是「Milvus 集成」这条风险路径（建集合能否带 BM25 Function、中文分词是否可用）。
向量化走的是 HTTP，与 Milvus 无关；`kb_document`/`kb_chunk` 是 MySQL 表，也不读 Milvus。
把这两块做掉不违反规矩，反而让 Milvus 探针通过后能立刻进入索引编排。

**② 为什么 `EmbeddingProperties` 与 `LlmProperties` 的方法重复也不抽基类**
两类的 `resolvedApiKey` / `maskedKey` / `resolvedBaseUrl` / `resolvedModelsPath` 几乎逐字相同（约 35 行）。
抽公共基类要改动 `LlmProperties` —— 那是 Phase 0–2.5 已上线、被反复验证的关键路径。
为一个纯形态优化去动它，收益 35 行、风险是整条对话链路，不划算；且这几段短逻辑每一段都对应一个
**已踩过的坑**（尾随空格 401、尾斜杠双斜杠、models 要退两段），抽出去后注释里的「为什么」会与调用方脱节。
**「三次重复才抽象」，这里刚好卡在第二次。**

**③ 为什么 `EmbeddingStartupProbe` 失败只 WARN（而 `LlmStartupProbe` 是 ERROR）**
向量化只服务**离线索引**：挂了的表现是「检索为空」，而 LLM 挂了是「每位在线居民立刻收到降级话术」。
用户可见程度不同，日志级别就该不同；两者都喊 ERROR 会让真正的线上故障淹没在噪声里。
同理，探活只调 `/models`（不产生 token 费用），且**「模型不在列表里」只提示不判失败** ——
该端点不返回全量（`text-embedding-v4` 就不在列表里但能调通）。

**④ 为什么 `EmbeddingBatch` 用「等长同序 + null 占位」，而不是过滤掉失败项**
调用方要把每条向量写回对应的 `kb_chunk.id`。过滤失败项会让返回下标与输入错位，
而分块正文里有大量**完全相同的模板句**（如「遵医嘱用药」），靠内容比对去猜哪条缺了必然出错 ——
错的后果是把 A 块的向量挂到 B 块上，检索时**毫无异常**，只有「答非所问」。

配套的两个判断：
- **降级只在 400 时做**（剔掉单条毒数据，其余仍可能成功）。401/模型名失效/429/5xx/网络故障一律视为致命：
  逐条重试会把一次失败放大成 N 次，**在已经限流时最糟**。
- **`EmbeddingClient` 没有流式方法**：向量化没有「逐字产出」的形态，套用流式抽象只会把
  「逐帧重试闸门」「首帧超时」这些用不上的机制拖进来。
