### 做法：抽出 `components/IconAi.vue`（新增，template-only SFC）

  **能命中的原因**：子组件根节点同时带父级 scope 标记，`scoped` 规则照常生效

### 新踩的坑：删 worktree 前必须先拆 node_modules 目录联接

为了让 worktree 跑构建，用 junction 复用了主仓库的 `node_modules`
（PowerShell：`New-Item -ItemType Junction -Path <wt>\psycare-web\node_modules -Target <主仓库同路径>`）。

—— 会顺着重解析点把主仓库的 node_modules 整个删掉。正解是**单参数**的非递归调用，
只移除链接本身；删完必须立刻断言主仓库 `<src>\.bin\vite.cmd` 仍存在，再
`git worktree remove --force`。

另外：`cmd /c rmdir` 虽然同样安全，但 **PowerShell 工具里调 cmd.exe 会被沙箱拒绝**
（`cmd.exe cannot be used from the PowerShell tool`）；反过来，
**在 Bash 里写含 `[System.IO.Directory]` 的 heredoc 会被误判成调 PowerShell 而拒绝**，
所以这类日志要用 Edit 工具写，不要用 `cat >>` heredoc。

## 调研：评测报告其实从来没有被保存过（10-23）

用户想在 AI 问诊页加「问诊」按钮看最近一次评测报告，前提是「每次完成评测都会生成一份报告」。
**这个前提不成立**，实测：

| 事实 | 证据 |
|---|---|
| `assessment` 表只有 9 列 | `id / resident_id / scale_id / total_score / raw_level / risk_level / crisis_flag / answer_json / created_at` —— **没有 advice、没有 max_score** |
| 建议文案是提交时现拼的 | `AssessmentService:140 .advice(buildAdvice(result))`，`buildAdvice` 在第 233 行，纯 switch |
| 前端也没有持久化 | `store.lastResult` 存在 **sessionStorage**（key `lastResult`），关标签页即失；只代表「本浏览器上一次提交」 |
| 两个读接口都缺字段 | `/assessment/history` 无量表名/满分/建议；`/assessment/{id}` 有 `scaleName` 但同样无建议 |

**好消息**：`buildAdvice` 是**纯函数**，只依赖 `crisis` + `riskLevel`，而这两个字段都在库里
（`crisis_flag` / `risk_level`）。所以「按历史记录重算建议」的结果与当时提交时**必然一致**
（除非中间改过文案）—— 不需要加列、不需要数据迁移。

**推荐方案**：新增 `GET /assessment/latest-report`（服务端一条 SQL 取最新 + 组装 VO），
而不是让前端串 3 个请求拼。关键理由：`/scale/list` **只返回 status=1 的量表**，
而 v12 给 scale 加了逻辑删除 —— 量表被管理员禁用/删除后，前端就查不到 `maxScore`，
百分比条会静默算成 0。服务端用 `selectById` 不受影响，还能回显「历史量表」。

另一个易错点：截图中「给您的建议」显示两条，不是后端返回数组，而是 `Result.vue` 的
`splitAdvice()` 拿一句话按「。」「；」拆开（A 级文案本身就是两句）。抽组件时这段必须一起搬。

### 二、右栏「最近一次测评」不刷新（真 bug，根因在 store 缓存短路）

**现象**：刚做完一份问卷 → 进 AI 问诊 → 右栏还显示上一次的分数，刷新页面才对。

**链路**：`Questionnaire.vue:153` → `store.submit()` → 落库 → 跳结果页 → 进问诊页
→ `AiChat.onMounted` 调 `store.loadHistory()` → **`if (history.value.length && !force) return`**
→ Pinia store 跨路由不销毁，`history` 还是上一次进问诊页时那份 → 直接返回旧数组。

**修法（`stores/assessment.ts`）**：新增 `historyStale` 标记 + 提交后置位并静默重取。

```ts
// submit() 成功分支末尾
historyStale.value = true
void loadHistory(true).catch(() => undefined)

// loadHistory()
if (history.value.length && !force && !historyStale.value) return history.value
history.value = await getHistory()
historyStale.value = false      // 只有成功才归 false
```

四个刻意的取舍：

1. **不清空 `history` 而只打标记**：清空会让卡片掉回「关联测评」兜底卡闪一下，留旧数据是原地替换；
2. **`void` 不 await**：提交页的按钮状态不该被这次「顺手刷新」拖住；
3. **失败吞掉但保留 stale**：下次 `loadHistory()` 会再取，而不是退回「缓存非空 → 短路」的老路；
4. **`AssessmentResultResponse` 里没有 `scaleId` / `createdAt` / `residentId`**，
   所以不能在本地凭响应「拼」一条 `Assessment` unshift 进去 —— 只能回服务端取真行。
   这也是没走「一行 unshift」那个更省事方案的原因。

`historyStale` 不对外导出：没有第二个调用方需要读它。

## 第 35 批：报告 / 医生视图的出口按钮改水平居中

用户要求：医生视图最下方那枚「回到对话」与报告内容下方那两枚按钮都水平居中，
各屏宽表现一致，不影响其他元素。

### 只有一处改动

两处按钮共用同一个容器 `.report-ops`（报告视图两枚、医生视图一枚），
所以只给这个选择器补 `justify-content: center` 就同时覆盖两处：

```css
.report-ops { display:flex; flex-wrap:wrap; justify-content:center; gap:10px; }
.report-ops .btn { flex: none; }
```

### 三个不显眼但必要的判断

- **不要用 `margin: 0 auto` 凑**：`.report-ops` 是 flex 容器，自动外边距只对
  「单个 flex item」生效；按钮组一换行（≤320px）就会失效。
- **`justify-content: center` 的自适应来源是容器宽度**：`.report-inner` /
  `.doctors-inner` 是 `max-width: var(--chat-col); margin: 0 auto`，
  所以按钮行对齐的是**内容列中线**而不是视口中线 —— 宽屏时两者重合，
  有右栏时只有前者才对（否则按钮会偏到右栏底下）。因此**不需要**任何窄屏断点。
- **`flex: none` 不能省**：居中和 `flex-shrink: 1` 同时存在时，窄屏先压按钮宽度，
  症状是文字间距被挤掉（`white-space: nowrap` 只保证不折行，不保证不被压）。

`.flex-wrap: wrap` 保留（原来就有）：极窄屏折成两行时每行仍居中。
纯 CSS 改动，未动模板与脚本，后端未动，刷新前端即生效。

### 实测到的三个硬事实（方案的地基）

1. **`doctor` 表没有排班/时段/诊室**：只有 `available`(1可接诊) 与 `current_load`。

### 三个关键设计判断

- **V1 不做在线支付**：无商户号/证书/公网回调；心理健康「先付费才能见人」有伦理问题；

- **4 张新表都不加 `is_deleted`**：预约/评价是业务凭证，状态用 `status` 表达。
  ⚠️ 实体类别加 `isDeleted` 字段，否则 MP 全局逻辑删除会让 `selectById` 静默过滤历史单子
  （`ScaleMapper.selectByIdIncludeDeleted` 就是为这个手写 `@Select` 绕过的）。
- **锁号必须 `UPDATE ... WHERE booked_count < capacity`**，影响行数 0 = 满；
  重复提交靠**函数唯一索引** `uk_active_slot ((IF(status IN (...), CONCAT(resident_id,'-',slot_id), NULL)))`

### 关键设计决定（下次改之前先读这段）

1. **2 张表，不预生成号源**。`doctor_schedule` 一行 = 某医生某天某时段，`capacity` 上限 / `booked_count` 已约。

2. **`appointment.booked_flag` 是 STORED 生成列**：`IF(status='BOOKED',1,NULL)`，参与唯一索引
   `uk_slot_resident(schedule_id, resident_id, booked_flag)`。唯一索引允许多个 NULL，
   于是「同人同时段只能一张有效单」由库兜底，**取消后还能再约**。
   ⚠️ 实体类**不能**声明 `bookedFlag` 字段（生成列不可写，会报 3105）。
3. **两张新表都不设 `is_deleted`**，实体也不声明 `isDeleted`。预约是业务凭证，
   挂逻辑删除等于「取消 = 查不到」且不报错（`ScaleMapper.selectByIdIncludeDeleted` 的前车之鉴）。
4. **`DoctorSchedule.bookedCount` 标了 `@TableField(updateStrategy = FieldStrategy.NEVER)`**：
   任何 `updateById` 都不会带这一列，防止内存旧值把刚 +1 的计数覆盖掉（覆盖了没人发现）。
5. **`notification.summary`** 是必须加的一列：前端拿 `content` 拼不出「医生 · 10-25 周六 09:00-09:30」。
   不加 `biz_id`（详情走弹层看 content）。
6. **时间格式化一律在服务端**：VO 给 `startText / timeText / whenText / shortText / weekday`。
   前端自己 `slice(0,5)` 迟早漏一处，界面上会出现带秒的时间；`weekday` 前端算还会踩 UTC 解析差一天。
7. **「已过期」不落库**，由 `AppointmentVO.getStatusKey()` 算（BOOKED + 开始时间已过）。
   全项目没有任何 `@Scheduled`，不为一个派生状态引调度器。
8. **`DoctorRow` 不复用 `RecommendedDoctors`**：网格卡 + 匹配依据 vs 横条卡 + 无匹配分，形态语义都不同。
9. **医生端原本没有通知页**（`/notifications` 只挂 DefaultLayout）→ 补 `/admin/notifications`，
   复用 `NotificationList.vue` + `admin` 开关（决定内边距由谁承担），路由用 `props: { admin: true }`。
10. **原生 input 而非 antd**：预约页用 `type=time / number / date`、原生 checkbox；

## 第 44 批 · 医生端「按周批量排班」：周一到周五 × 5 个时段，一键铺两周（2026-10-23 下午）

### 需求原话
「医生固定周一到周五都有工作时间段，你可以添加四五个时间段」

### 落地形态
配置页顶部加一张**批量排班卡**，默认值已经填好，点一次按钮就铺完：
- 周几默认勾 **周一~周五**；铺几周默认 **2 周**（上限 4 周）
- 模板默认 **5 段**：09:00-09:30 / 09:30-10:00 / 10:00-10:30 / 14:00-14:30 / 14:30-15:00，每段上限 3 人
- 「+ 加一个时段」自动接上一段结束时间、+30 分钟、沿用上限
- 「覆盖已有时段上限」默认**不勾**（保护医生手工调过的值）

### 新增接口 `POST /schedule/weekly`
入参 `WeeklyScheduleRequest`：`fromDate? / weekCount(1~4) / weekdays[](1~7，默认 1~5) / overwriteCapacity / slots[](≤12)`
出参 `WeeklyScheduleResultVO`：`dayCount / created / updated / skipped / dates / summary`
`summary` 由服务端 `getSummary()` 拼好（「已为 9 天生成号源：新增 45 段、跳过 5 段」），前端不再重算语义。

### 与 `/batch` 刻意不同的三处行为（都写进了 Service 注释）
1. `fromDate` 早于今天 → **静默收敛到今天**，不报错（昨天开的页面今天点，是正常操作）
2. 今天已经开始的时段 → **跳过不建**（建出来居民端会过滤、医生端却看得见，界面自相矛盾）
3. 单段 capacity < booked → **跳过并计数**，不整批回滚（否则一条历史数据让「铺两周」永远失败）

### 关键实现点
- 抽出 `validateAndSort()`，单日与批量共用一份校验（分开写迟早一边放宽规则）
- 区间内已有行**一次查出**进 `Map<"日期|开始时间", DoctorSchedule>` 索引：4 周 × 5 天 × 12 段最多 240 次 upsert，逐条 `selectOne` 就是 240 次往返
- 键 `slotKey = date + "|" + start` 与 `uk_doctor_date_start` 同构
- `@Transactional(rollbackFor = Exception.class)`（纯 DB，无外部调用，符合红线 #9）
- `MAX_WEEKS = 4`，与 `MAX_DAYS = 30` 同量级：批量铺的天数若超过配置页能看到的窗口，后几天就再也没有入口能改

### 前端 `DAYS_AHEAD` 14 → 28
必须与 `MAX_WEEKS × 7` 同步改。只改一侧就会出现「生成了 4 周号源，但页面只能看 2 周」。

### 按钮上的「N 天」怎么算
`previewDays` 从**服务端返回的 `days`** 里筛（不在前端算日期，`new Date('2026-10-25')` 按 UTC 解析会差一天）；
并且额外排掉「今天的时段已经全部过去」的日期 —— 否则下午 4 点打开会「按钮说 10 天、提示说 9 天」。
用 `toMinutes()` 换成分钟数与当前时刻比较（字符串比不了）。

`markNoticeRead()` 只做本地 `noticeCount - 1`：调用方已经发过 `POST /{id}/read`，
而「点开一条 = 减一」在这里是确定的（不像会话数要看服务端汇总）。
`Math.max(0, …)` 是为了防止轮询未回来时减成 -1，让 `badgeTip` 显示「-1 条未读」。

### 已定的行为

- 轮询沿用 `inbox` 的 15 秒 tick，不新增定时器

## 第 49 批 · 首页底部改三栏：最近记录收窄 + 新增「服务引导 + 四项保障」（2026-10-23 傍晚）

### 需求原话
「左下角最近记录卡片的区域能否塞进两个卡片，把"最近记录"卡片长度减小，参考如图，注意banner图位置格式不变。再帮我生成UI」

### 布局：`1 : 0.95 : 1.45`（内容宽 1288 − 40 间隙 = 1248 → **367 / 349 / 532**）
- ① 最近记录：691 → **367**（短 47%），行形态重做
- ② 新增中栏：服务引导卡 + 四项保障条
- ③ Banner：位置 / `align-self:stretch` / 虚线占位 / `1200×480·2.5:1` 标注**全部不动**，只有列宽变

### Banner 代价（算过，不是估的）
| | 两栏 | 三栏 |
|---|---|---|
| 列宽 | 576 | 532 |
| 高度 | 260 | 273 |
| 比例 | 2.21:1 | **1.95:1** |
| cover 两侧各裁 | 5.7% | **11.0%** |

`cover` 裁切公式：容器 w×h、物料 2.5:1 → 缩放后图宽 = h×2.5；裁掉比例 = 1 − w/(h×2.5)。
273×2.5 = 683 → 532/683 = 77.9% → 两侧各 11.05%。
**第一稿说"三栏会裁 37%"是按三等分（各 416）算的**；不均分就不会。运营图主体需落在中间 78%。

### 最近记录行形态重做（4 处关键）
1. **状态胶囊必须白底**（`--chip-bg` 90%）：行底已是 `--risk-*-soft`，标签再用同族 soft = 没有标签。
   合成底 `#fdfffe` / `#fffefd` 上 ink 分别 **5.20 / 5.06** ✓
2. **箭头用 `--text-2` 而非 `--text-3`**：实测 text-3 在两档行底只有 **4.31 / 4.42** ✗；同行的 text-2 有 7.02 ✓
3. **去掉右侧分数**：hero 内嵌卡已经显示分数，且 367 宽下「分数 + 等级」竖排会占 60px 把量表名挤断
4. **去掉卡头计数 chip**：367 宽下它只会挤掉标题
5. `.rec-list{flex:1}`：中栏 273 比列表自然高（245）多 28，空白落在卡底，卡本身等高

图标改成语义化：PHQ-9 心形、PSQI 月牙、GAD-7 云、PHQ-15 脉搏线（原来是统一的「i」圆圈，无意义）。

### 中栏两张卡的三个约束
1. **服务卡标题 19px serif 两行**（`<br>` 硬断）：349 宽下 17 字一行放得下，但两行才有参考图的呼吸感
2. **四项保障 1×4 而不是 2×2**：四块各 76px 时 2×2 更宽松，但那条高度会从 ~99 翻到 ~198，
   底部被拉到 370 → Banner 比例掉 1.44:1（各裁 20%）。宁可说明文字压到 ≤7 字
3. **植物用矢量剪影（`--care-plant` .20）而不是实拍图**：与「整页只有一张插画底」一致，且不多一次图片请求

### 响应式的三条（顺序不能乱，`@media` 不加权重）
- **≤1180**：保障条 1×4 → **2×2**（中栏压到 328 时每块 71px，6 字说明贴边）
- **≤1100**：底部单列 → 中栏从纵向改 **`grid 1.1fr / 1fr` 左右并排**
  （单列后中栏 1224 宽，纵向叠会让服务卡右侧空出 880px 白底 + 一团不知道往哪放的光晕）
- **≤720**：中栏回纵向（手机一行放不下并排两栏）
