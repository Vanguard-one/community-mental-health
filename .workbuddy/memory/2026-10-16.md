## 修：登录页首屏最右一条 1px 蓝色竖线

**现象**：`/login` 刚进「选身份」那一屏，卡片最右侧有一条竖的蓝色细线；切到表单屏就没了。

**根因**：`.auth-action`（白色操作页）用 `left: 60%` + `width: 40%` 覆盖卡片右半边。
两个百分比各自落到布局单位（1/64 px）后相加与容器实际宽度差半像素 → 右边缘漏出
`.auth-card` 的蓝色渐变底。表单屏看不见，是因为那时白板在左侧、右半边本来就该是蓝的。

**改动**：`psycare-web/src/views/auth/Login.vue`，只改 `.auth-action` 的定位两行 ——
`left: 60%; width: 40%` → `right: -1px; width: calc(40% + 1px)`。
外扩 1px 是方向不对称的保险：`.auth-card` 有 `overflow: hidden`，多盖被裁掉、少盖必然露线。
宽度同步 +1px 使左边缘仍在 60%，`translateX(-150%)` 与 2:3 比例无需改动。

**自检**：`vue-tsc -b` 0 error；`vite build` ✓（2.28s）；`vendor-antd` **714.54 kB**（预算 800 kB）。

**结论已沉淀**：硬约定 **#122**。

## 修：AI 问诊页发送按钮文字偏下

**根因**：`.chat-input :deep(.ant-btn)` 只把 `height` 从 38 压到 32，没动 antd 的 padding ——
antd 按钮是 `display: inline-block`，上下内边距按 `controlHeight`(38) 算（`padding-block ≈ 6.21px`，
配 `line-height 1.5714` 恰好凑满 38px）。高度压到 32 后内容盒矮了 6px，而行盒仍 23.57px 且
从**内边距上沿**铺开 → 文字整体下沉约 2px，胶囊按钮上肉眼可见。

**改动**：`psycare-web/src/views/consult/AiChat.vue` 的 `.chat-input :deep(.ant-btn)` ——
补 `display: inline-flex; align-items: center; justify-content: center`。
交给 flex 居中后，垂直对齐不再依赖「padding 与 line-height 恰好凑够」这种巧合，
以后换字号 / 改 `controlHeight` 都不会再错位。

## AI 问诊「清空会话」弹窗：改三选一 + 居中

**文件**：`psycare-web/src/views/consult/AiChat.vue`（单文件改动，后端一行未动）

**① `Modal.confirm` → 组件式 `<a-modal centered>`**。原实现只有「确定 / 取消」两个出口，
承载不了「两种清空」。改用 `a-modal`（**已由 unplugin-vue-components 按需注入，不进
`vendor-antd` 预算**，同 `AssessmentHistory` 的逐题弹窗）+ `:footer="null"` 自绘底栏。
`centered` 必写：a-modal 默认 `top: 100px`，这张弹窗只有一屏内容，贴顶会让视觉重心上浮。
⚠️ 弹窗内插槽节点**编译时带上了本组件的 scope 属性**（Teleport 只搬 DOM、不摘属性），
所以 scoped 样式对 `.cm-*` 生效；但**刻意不写任何 `.ant-modal-*` 覆盖规则** ——
那些类名不在 scoped 作用域里，只能 `:deep` 穿透，antd 升版改类名就会静默失效。

**② 三个按钮的中文名（用户原名为临时拟定，本次替换）**：
| 位次 | 名称 | 语义 | 视觉权重 |
|---|---|---|---|
| 左 | **暂不清空** | 什么都不做（原「取消」） | 中性描边 |
| 中 | **只清空聊天记录** | 删消息，`summary` 保留 → AI 仍记得 | 主色描边 |
| 右 | **清空并重置记忆** | 删消息 + 关旧会话 + 开新会话 → 从零开始 | 实心 `--risk-d-ink` |

三者的区分字是 **「暂不 / 只 / 并」**，权重左→右递增 = 影响左→右递增。
弹窗正文另给两个选项各一句后果说明（颜色只承担权重，**区分依据是文案**）。

**③ 「重置记忆」的真正做法（最容易踩的坑）**：不能只丢前端 `sessionId` ——
后端 `openSession` 每个居民只保留一条 OPEN 会话、已有就复用，丢掉 id 再 open
会把旧会话连同 `summary` 一起还回来（静默无效）。必须 `close()` → `startNewSession()`。
顺序是「**先删消息 → 再关会话 → 最后开新的**」（`close()` 的 finally 会置空 sessionId）。
`close()` 抛错时补 `chat.enter()` 退回，避免停在「会话未建立」的假故障态。
**刻意不继承 `assessmentId`**：这一项的定义就是「从零开始」，带上测评背景就不叫从零了。

**④ 头部按钮的 disabled 判据跟着改**：原来是 `!chat.hasMessages`。但选过
「只清空聊天记录」之后消息没了、`summary` 还在 —— 按原判据按钮会灰掉，
「清空并重置记忆」**永远点不到**，而那正是最需要它的场景。改为 `canClear` computed：
`sessionId !== null && !sending && (hasMessages || !!summary)`。

**⑤ 顺带修掉的对比度问题**：`.ghost-btn.is-primary`（「开启新会话」）原为
`--primary-soft` 底 + `--primary` 字 = **4.44:1**，差 0.06 不达 AA → 字色改 `--primary-dark`（5.76 ✓）。
同一条判据，同一个文件里不宜一正一反。

**自检**：`vue-tsc -b` 0 error；`vite build` ✓（2.13s）；`vendor-antd` **714.54 kB**（零膨胀）；
`check_ref_value.py` 67 个文件无漏写 `.value`；`onClearMessages` / `Modal` 残留为 0

**结论已沉淀**：硬约定 **#124**（危险实心按钮只能用 ink 填充）、**#125**（重置记忆必须先 close 再 open）。

## 诊断：AI 回复「稍微有点慢」的根因（**只测量，未改代码**）

> 数据来源：真库 `ai_usage_log` **81 条**有效记录 + 对 DeepSeek 的**对照实验**（9 次）。
> 结论全部来自实测，不含推断。

### 一、延迟构成（生产数据）

| 指标 | 中位 | 尾部 |
|---|---|---|
| 首帧 | **1530 ms** | 最大 10701 ms |
| 总耗时 | 1833 ms | 最大 11577 ms |
| **首帧占总耗时** | **83%** | —— |
| reasoning tokens | 161 | 最大 1468 |

耗时 > 3s 占 17%、> 5s 占 9%、> 8s 占 4%。

**回归**：`首帧 ≈ 532 ms + 6.2 ms × 思考token`（**corr = 0.968**）。
而 `corr(首帧, prompt_tokens) = 0.192`、`corr(首帧, cached_tokens) = 0.016` ——
**prompt 长度与缓存命中都不是瓶颈**，思考量是唯一显著变量。

**532 ms 是地板**：实测复用连接下的最小往返（`max_tokens:1` + 关思考）
= 453 / 487 / 547 / 808 ms；TLS 新连接 209~343 ms。生产最小值 486 ms 已贴到地板。

### 二、对照实验（同题同 prompt，各 2 次）

| 参数 | 首帧 | 思考字数 |
|---|---|---|
| 不传（默认 high） | 5391 / 2363 ms | 945 / 389 |
| `effort: low`（**当前配置**） | 2657 / 2081 ms | 431 / 349 |
| `reasoning_effort: low` | 2519 / 4879 ms | 481 / 848 |
| `reasoning_effort: none` | **615 / 827 ms** | 0 |
| `thinking: {type: disabled}` | **737 / 931 ms** | 0 |

🔑 **关思考后首帧 615~931 ms，稳定快 2.5~5×**。且 `effort: low` 是**生效的**
（与 `reasoning_effort: low` 同量级）→ 不存在「参数名写错被静默忽略」的 bug。
⚠️ **同参数同输入首帧在 2.0s 与 5.0s 间波动** → 思考量本身不稳定，调参不如按场景分流可靠。

### 三、⚠️ 关思考的质量代价（危机语境实测）

输入：AI 已问「有没有出现过伤害自己的念头」，用户答「晚上会想睡过去不醒，但我妈还在」。

- **开思考**（首帧 14648 ms）：分层提问 + **给出 120/110/12356/400-161-9995 与安全措施**（不独处、危险物品交人保管）
- **关思考**（首帧 1048 ms）：共情到位、追问一句，**但没有给任何热线与安全兜底**

→ **绝不能全局关思考**。安全出口的产出恰好落在思考过程里。

### 四、已核实的外部事实（**不要再凭记忆写**）

DeepSeek `/v1/chat/completions` 思考相关参数（2026-10-16 取自官方 API 文档）：
- `thinking` object，子字段 `type` ∈ [`enabled`, `disabled`]，默认 `enabled`；`disabled` = 切非思考模型
- `reasoning_effort` ∈ [`none`, `low`, `high`, `max`]，默认 `high`；`none` 禁用思考；
  `minimal`→`low`，`medium`/`xhigh`→`high`
- `reasoning_content` 仅思考模式返回；`max_tokens` 不给时默认 **非思考 8K / 思考 64K**（`max` 档 128K）
- 思考模式下 `temperature` 无效；`tool_choice: required` 会 400（须先关思考）
- 服务端 `/models` 实返两个：`deepseek-flash`、`deepseek-v4-pro`（无第三档）

### 五、另外两处观测缺陷（优化前必须先修，否则无法验收）

1. **`retrieved_count` 被硬编码**：`AiUsageRecorder:56` 是 `row.setRetrievedCount(0)` ——
   永远为 0，**无法判断 RAG 到底注没注到资料**。而检索在关键路径上。
2. **前置链路完全没进计量**：`AiUsageRecorder` 的 `first_token_ms` 从
   `AiConsultService:596` 的 `startedAt` 起算，而该行在 `saveMessage` / `retrieveRaw` /

   **全都不在任何指标里**。用户真实等待 = 未计量前置 + 首帧。

**未动一行代码**（本轮只做测量与方案）。待用户选定方案后再实施。

**清空它们即退化为纯 B**，改成 `enabled` 即退回改造前行为 —— 不需要再改代码。

### 参数组合的实测（**这轮新验证，之前是推断**）

| 组合 | 思考字数 | 首帧 |
|---|---|---|
| `thinking=enabled` + `effort=low` | 995 | 3782 ms ← 开这条路实际发的 |
| `thinking=enabled` 单独 | 1749 | 5704 ms |
| `thinking=disabled` + `effort=low` | 0 | 813 ms |
| `thinking=disabled` 单独 | 0 | 847 ms ← 关这条路实际发的 |

→ `enabled` 与 `effort` **能正确叠加**（思考量近乎减半）；`disabled` 会压过 `effort`。
但仍**关思考时不发 effort**：不该让「关掉思考」依赖一条文档没写、只靠实验观察到的优先级规则。
另：开思考时**显式**发 `thinking:{type:enabled}`，不吃服务端默认值 ——
默认值一旦被上游改成 disabled，「保安全」那条路径会**静默退化**成最速路径（日志/指标全正常）。

### 三条可复用规则

① **推理模型的「思考量」是首帧延迟的唯一有效杠杆**：`corr(首帧, 思考token)=0.968`，
而 `corr(首帧, prompt长度)=0.192`、`corr(首帧, 缓存命中)=0.016`。
压提示词、提缓存命中在推理模型上**基本无效**，先量再说，别按「长 prompt 就慢」的直觉优化。

② **首帧占总耗时 83%** —— 优化推理模型体验时，「等待期有没有反馈」的收益
可能和「真实提速」同级：用户 83% 的等待里屏幕是空的。

③ **能用「调用前就已知道的状态」做的分流，别用额外请求做**：
阶段（Redis，第一行就读完）与风险等级（本轮本来就要查的那一行）都是现成的，
所以思考开关是零成本的确定性决策。若改成「先问模型该不该思考」，那是自相矛盾。
