## Phase 8.3：消息列表只列「有过消息」的人

**需求**：两端消息列表都只展示曾经有过消息往来的居民 / 医生；从未发过消息、没有消息记录的不出现。
（用户同时要求说明「实现方式」与「有过消息」的判定条件，答案已写进 `ChatService` 类注释 + `开发文档.md` 9.6。）

### 判定条件：该会话下至少存在 1 条 `consult_message`

四个「不看」——不看方向、不看条数、不看会话状态、不看已读。
最关键的一条取舍是**不要求双向**：若要求「双方都发过」，刚发出消息、对方还没回的那条对话
会在**两端列表同时消失**，与自己刚做的事直接矛盾。

### 实现：过滤下沉到 SQL（前端不做二次筛选）

| 位置 | 改法 |
|---|---|
| `ChatMapper.selectSessionList` | WHERE 加 `AND EXISTS (SELECT 1 FROM consult_message m WHERE m.session_id = cs.id)` |
| `ChatMapper.selectDoctorList` | 子查询内 `MAX(cs2.id)` **也**加同样的 `EXISTS`；外层加 `AND cs.id IS NOT NULL`；删掉恒 false 的排序键 `cs.id IS NULL` |
| `ChatService` | 类注释新增「有过消息的判定条件」小节；`listSessions` / `listDoctors` 注释同步 |
| `MessageList.vue` | 空态文案改「还没有居民和你聊过」；预览兜底加注释 |
| `MyMessages.vue` | 页头/空态文案改消息列表语义；按钮统一「继续聊天」；删掉不可达的「已建立对话，还没有消息」分支及其 CSS |

**动因**：`consult_message(session_id)` 上有 `idx_session`，`EXISTS` 走索引；用半连接而非 JOIN，
是因为 JOIN 会被同一会话的多条消息复制成多行、还得再 DISTINCT。
过滤放 SQL 是为了让会话列表 / `messageCount` / 侧栏待回复角标（`AdminLayout` 直接复用 `listSessions()`）
三处口径同源。

### 踩到的点 ⚠️

**`selectDoctorList` 的 `EXISTS` 必须写两处，少一处就漏**：
子查询里那处决定「取哪条会话」—— 不写会在**最新会话恰好是空会话**时挑中它、跳过更早有消息的那条；
外层 `cs.id IS NOT NULL` 决定「这行留不留」。只写外层、以为已经过滤干净，是这里最容易犯的错。

### 核实到的关键技术参数（避免凭记忆写错）

| 项 | 值 |
|---|---|
| 通义千问 base-url | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| chat 路径 | `/chat/completions`（**注意与 base-url 的 v1 会双拼**，现有 `DeepSeekClient` 用 `.uri("/v1/chat/completions")`） |
| embedding | `text-embedding-v3`，1024 维默认（可 768/512），最大 8192 token，**批量上限 10** |

### 设计要点（详见文档）

- **通义千问**：`DeepSeekClient` 无任何 DeepSeek 专有逻辑 → 泛化为 `OpenAiCompatClient`，
  base-url 带 v1、`.uri` 改相对路径，一个类吃下 DeepSeek/Qwen/GLM/Kimi。
- **异常四道防线**：错误归类（401 不重试 / 429 退避 / 400 压缩上下文后重试）·
  **首 token 超时**（15s，与整体 60s 分开）· **流内错误协议**（改 `Flux<ServerSentEvent>`，用 `event:error`；
  ⚠️ 前后端必须同改，否则前端把 error 的 data 当 token 拼进气泡）· 降级话术（**必须带 12356 人工出口**）。
- **引导问诊**：五阶段（联结→主诉→功能影响→风险筛查→小结转介）。路线 A 纯 prompt（零 DDL，推荐先做），
  路线 B 阶段状态机（`consult_session.stage` 或 Redis —— pom 注释早就写着「Redis：AI会话上下文」但**当前并未使用**）。
- **RAG**：父块 1200-1500 字 / 子块 300-500 字 + overlap 50；**父块不存向量**；
  存储起步用 **MySQL + 应用层余弦**（`kb_document` / `kb_chunk`，1 万块 ≈ 40-80 MB），
  抽象 `VectorStore` 接口预留 Milvus/Qdrant；检索建议混合（稠密 + ngram 全文，RRF 融合）；
  **阈值过滤是防幻觉的关键**（需用真实语料校准，医疗场景宁严勿松）。
- **RAG 的注入点在 `buildMessages`**，**必须在流开始前同步完成**（流式过程中无法回退）；检索失败要降级为无 RAG 继续，不阻断。
- **RAG 本身就是一种工具**：Phase B 预检索 → Phase C 演进为 `searchMedicalKnowledge` 工具（Agentic RAG），
  用同一套 `AiTool` 抽象，演进不需重写。
- **MCP 路线**：先做本地工具跑通 function calling 循环（⚠️ 工具调用中间态**不能流式**，需分两段），
  再加 `McpToolAdapter`。医疗场景**每个工具都要审计 + 入参脱敏 + 白名单**（`userId` 必须服务端注入，
  不能让模型生成）——与上面的越权修复是同一类问题。

## AI 助手开发计划定稿（选型变更：DeepSeek + Milvus）

用户确认三项决策后产出 `AI助手开发计划.md`（1156 行 / 65 KB），**取代**上一份设计文档中
「通义千问接入」与「MySQL 存向量」两节。

**核实到的三条硬事实**（当日实查，非记忆）：

1. **DeepSeek 无 embedding 接口** —— 只有 `deepseek-v4-flash` / `deepseek-v4-pro` / vision 实验模型。
   RAG 必须「DeepSeek 生成 + 第二家向量化」。`EmbeddingClient` 必须是接口 + 配置选实现。
2. **`deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 退役**，调用直接失败无回退 ——
   项目 `application.yml` 配的正是 `deepseek-chat`，**改配置前 AI 对话根本调不通**（这解释了"未验证"待办）。
3. **Milvus 2.6 向量字段不可为 NULL** → 父块不进 Milvus、只留 MySQL（恰好是更正确的分层）。

**架构核心判断**：MySQL 是事实源、Milvus 是可重建索引层 → **先写 MySQL 后写 Milvus**，
Milvus 失败仅告警（rebuild 能补）。Milvus 2.6 内置 BM25（`Function type=BM25` + `SPARSE_INVERTED_INDEX`
+ `RRFRanker(60)`）正好补上 DeepSeek 缺 embedding 的短板，混合检索不必引外部稀疏向量接口。

**AI 助手详细设计要点**：提示词按稳定性分 8 层（固定前缀严禁时间戳/id，否则 DeepSeek 上下文缓存
100% 不命中且不报错）· 五阶段阶段机（**规则裁决 + LLM 建议**）· token 预算 + 摘要落 `consult_session.summary`（零 DDL）·
SSE 六类事件协议（**前后端必须同批改**）· 四道防线（错误归类/首 token 超时/流内 error 事件/带 12356 的降级话术）·
工具 `ToolContext` 服务端注入 userId · usage 与工具调用双审计表。

**Milvus 已核实的坑**：BM25 那路必须 `new EmbeddedText(text)`（否则 issue #1402 的
`Search target vector type is illegal`）· **中文 BM25 需配分词器**，默认按空格切会让中文召回归零（探针实测确认）·
collection 要先 `loadCollection` · 索引与查询度量必须同为 COSINE · Java SDK 2.6.22 对齐服务 2.6.x。

## 12:06 · 修 `resolvedModelsPath()` 推导 bug（用户重启后第一次真跑就炸）

**现象**：重启后启动探活报
`❌ 失败 code=LLM_UNKNOWN：上游 404：（探活路径 /chat/models）`。

**定位**：不是密钥问题 —— `curl --noproxy '*' https://api.deepseek.com/v1/models` = **200**，
`.../v1/chat/models` = **404**。是路径推导错了。

**根因**：`resolvedModelsPath()` 原本写的是 `substring(0, lastIndexOf('/')) + "/models"`，
即只砍掉**动作段** `/completions`，于是 `/chat/completions` 推出 `/chat/models`。
正确的是去掉**末尾两段**（资源段 `/chat` + 动作段 `/completions`）再接 `/models`：

```
/chat/completions                    → /models      ← 本项目实际（base-url 已含 /v1）
/v1/chat/completions                 → /v1/models
/compatible-mode/v1/chat/completions → /compatible-mode/v1/models
```

原理：`models` 与 `chat` 是**同级**资源，都在版本段之下，所以资源段也要去掉。

**为什么能潜伏到现在（真正的教训）**：模型连通性是早期用 Python 探针
（`llm_probe.py`）验的，而那个脚本**把 `/v1/models` 写死**了；Java 侧走的是推导。
两条路径从没交叉验证过，于是「Java 启动探活」第一次真跑就暴露。
**推导逻辑必须用自己的产物验一次，不能拿另一条路径的结论当证据。**

**改动**
| 文件 | 改动 |
|---|---|
| `LlmProperties.java` | `resolvedModelsPath()` 重写为「去末尾两段」；显式配置也 trim；新增 `resolvedBaseUrl()` 去掉 base-url **尾部斜杠**（`.../v1/` + `/chat/completions` → `//chat/completions`，部分网关直接 404 且与「路径写错」表现一致） |
| `OpenAiCompatClient.java` | WebClient 改用 `resolvedBaseUrl()`；探活失败信息从「探活路径 /chat/models」改为**打完整 URL** —— 404 时才能一眼区分「推导错」还是「base-url 错」 |
| `application.yml` | `models-path` 注释写清推导规则与两种例子，并提示「探活日志会打完整 URL，照它填最直接」 |

**验证方式（这次刻意换了做法）**：写 `target/PathCheck.java` 用**真实 `LlmProperties` 实例**
跑 15 项断言（3 种 path × 推导 / 显式配置优先 / trim / base-url 尾斜杠 / key 三态与脱敏 /
`toString()` 不含明文密钥），全部 **PASS**，随后删除临时文件。

## 五个非显然的决定

1. **阶段机是纯函数，在线推进与 Redis 丢失重建共用它。**
   `StageRules.advance` 不读 Redis、不查库、不看时钟。若两条路径各写一份判定，
   差异不报错，只表现为「偶尔跳到别的阶段」—— 最难复现、最难被相信的一类 bug。
2. **`turnsInStage` 与 `turns` 必须分开。** 用总轮数做阈值会让阶段一路冲到结尾，
   五阶段退化成一次性问答。跨阶段时 `turnsInStage` 归零。
3. **每轮最多进一级**（`decide` 用 switch 不用 while），防止一轮连跳两阶段。
4. **token 预算不引入 tokenizer。** CJK 1 字≈1 token，其他 4 字符≈1 token，每条 +8。
   预算只是安全上限，估偏 20% 无影响；多一个依赖不划算。
5. **阶段信息塞在 `meta` 里，不新开 `stage` 事件。** 阶段在请求开始**前**就定了，
   属「本轮元信息」，与 sessionId/model 同类。每多一种事件类型就多一处必须同步的契约。

## ⚠️ 顺序陷阱（已写进 `StageStore` 类注释）

**必须先 `load` 再落库本轮消息。** 重放会把库里已有消息全算进去；
若先 `saveMessage` 再 `load`，重放已推进一次，调用方再 `advance` 一次 = **推进两次**。
表现为阶段走得莫名快，且**只在 Redis 冷启动 / TTL 到期时**出现（有状态时看不出）。

## 自检发现并修掉的真实缺陷

`FIELD_WORDS` 的「时长」组只收了「几个月」，**漏了「个月」** →
「大概两个月了」抽不到 `duration`，主诉阶段无法判定信息够不够。
这类漏词**不报错**，只让阶段推进比预期慢。结论：**词表要靠真实语料回归，不能靠想。**

## 为什么输出侧要另立判据（本次核心）

| | 检测对象 | 判据 | 口径 | 误报代价 |
|---|---|---|---|---|
| `hit` | 居民输入 | 危机词出现 | 宁宽 | 多一句热线提示（可接受） |
| `harmful` | 模型输出 | 危机词 + 操作性词共现 | 宁窄 | 正常对话被判成危机（本次故障） |

操作性词**刻意不收「怎么/如何」**：它们与「你怎么会有这种念头」高频共现。
只收：方法/方式/步骤/教程/指南/操作/流程/剂量/致死量/几片/几颗/多少片/多少颗/吃多少/吞多少/多少药。

**两条路径文案必须分叉**：`INPUT` 真建 CRISIS 工单 → 可承诺「已转接人工」；
`OUTPUT` 不建工单（模型失言 ≠ 用户危机，凭一次失言贴危机标签是另一种伤害）→
`safetyNotice()` 不承诺。「不会兑现的承诺比不承诺更伤人」。

### ⚠️ 阈值与时序陷阱（本轮唯一的真实缺陷）

**推进发生在「用户发言之后、组装提示词之前」**：

最终：`OPENING → turnsInStage >= 2`；`CHIEF_COMPLAINT → (key >= 3 || turnsInStage >= 2)`；合计 **2~3 问即转介**。

## 应允判定：为什么必须「一问一答」

前端只看得到后半 —— **任何一轮的「好的」都长得像应允**（可能只是在回答「最近睡得怎么样」）。
第 1 半「AI 上一轮问过没有」只有服务端看得到（要回看上一轮 AI 回复原文）。

```java
public static boolean accepted(String lastAiText, String userInput) {
    if (containsAny(input, NO_WORDS)) return false;   // ← 否定优先
    if (wantsDoctor(input)) return true;              // 主动要医生不必等问
    return askedForReferral(lastAiText) && containsAny(input, YES_WORDS);
}
```

- **否定必须优先**：中文否定与肯定**共享字形** —— 「不用」含「用」、「不要」含「要」、
  「不好」含「好」、「不行」含「行」、「不对」含「对」。不先判否定，「不用了谢谢」会被读成应允
  → 动画弹出、会话被关，用户一脸茫然。
- **`ASK_MARK` 是隐式契约**：`ReferralRules.ASK_MARK = "需要我为你推荐合适的医生吗"` 必须与
  `PromptAssets.INTERVIEW_FLOW` 第 3 阶段的固定收尾问句**逐字一致**，改一处必须同步另一处，
  否则判定**静默失效**（不报错，只是永远不触发）。
- 判定写宽松（`推荐 && 医生 && (吗|？|?)`）以容忍模型改写，但**疑问句检查不是可选项** ——
  否则「医生可能会推荐……」这类陈述句会命中。
- 后端三重门槛：`turns >= REFERRAL_MIN_TURNS(2)`（第一句就说要找医生不该立刻跳走）
  → 已在转介阶段或主动要医生 → `accepted`。
- `lastAiText(sessionId)` **只取 1 条、按 `id` 倒序**（同秒落库 `created_at` 相同，按时间排序不稳定）。

## SSE `recommend` 的位置与互斥

| Pinia store | **全局单例**，路由切走不销毁 |
| `AiChat.vue` | 只有 `onMounted`，**没有 `onUnmounted`** → 离开后 `messages` / `sessionStatus` 全留在内存 |
| `chat.close()` | 只 `sessionId = null` + `persist(null)`，**`messages` 数组原封不动** |
| `chat.open()` | 建新会话成功后**不清视图**（它假定调用方已经 reset，但 `onMounted` 直接调它） |

复现路径：点「推荐医生」→ `close()` 清了 localStorage 但没清消息 → 跳 `/ai-recommend` →
再点菜单「AI 问诊」进来 → `restoreLast()` 因 localStorage 已空而 false → `open()` 建新会话 →
**新 sessionId 配上一次的完整对话**。顶部显示「会话 #新ID，内容仅用于本次咨询」看着完全正常，
底下却是旧内容 —— 更糟的是继续发消息时服务端上下文是空的，用户会以为「AI 怎么不记得我说过」。

### 改法（两层，`useChatStore` 仅 `AiChat.vue` 一处使用，改动面收敛）

1. **`stores/chat.ts`**：抽出 `clearConversation()`（messages / summary / 危机态 /
   `recommendAccepted` / `lastFailedText` / stage 那一半），`open()` 成功建会话后先调它、再写新 id；
   `reset()` 复用它 + 清 sessionId/persist。
   —— 分成两份写迟早漏字段，漏的那个不报错、只在界面上露出来。
2. **`AiChat.vue`**：新增 `onUnmounted(() => chat.reset())`。

### 关键：为什么加 `onUnmounted` 不会破坏「刷新恢复」

**`onUnmounted` 只在 SPA 内部路由切换时触发，F5 刷新不触发**。所以两条路径各走各的：

| 动作 | 结果 |
|---|---|
| 点菜单进本页 | onUnmounted 已清过 → 全新会话 |
| 浏览器刷新 | store 内存本就空 + localStorage 有 → `restoreLast()` 恢复上次会话 |

原设计意图（不恢复则「刷新一次就像换了个人」）完整保留 —— 所以 `onMounted` 里的
`restoreLast()` **不要去掉**，它和 onUnmounted 并不冲突。

另外 `onUnmounted` 里**只清前端、不关服务端会话**：用户可能只是切去看一眼测评结果、
打算回来接着聊，替他关掉是越权。未关闭的会话留在「历史会话」里供主动点回。

grep 确认 `psycare_ai_last_session` 全项目只在 `stores/chat.ts` 读写、两个推荐页
（`AiRecommendResult` / `DoctorConsult`）都不依赖 chat store → 改动不会波及它们。

## 医生端侧栏固定（AdminLayout）

**症状**：医生端「用户信息」页内容较长，页面一滚动，左侧 232px 菜单栏跟着一起滚出视口。

**根因**：`.sider` 只是普通 flex 项。父级 `.admin-layout` 是 `flex-direction: row`，
默认 `align-items: stretch` 把侧栏拉到与右侧内容**等高** —— 侧栏自身高度 = 整个滚动区间，
于是在它身上 `position: sticky` 即便写了也没有可粘的余量（表现就是"一起滚"）。

**修法**（`layouts/AdminLayout.vue` 的 `.sider`，纯 CSS 五行）：
`position: sticky; top: 0; align-self: flex-start; height: 100vh; overflow-y: auto; z-index: 20;`

**为什么判定 sticky 可靠、而不是大改滚动模型**：`html/body/#app` 只有 `min-height: 100vh`、
无 `overflow` → 滚动容器是**文档根**；且右侧 `.header` 早就用 `position: sticky; top: 0` 且工作正常
（用户从未抱怨标题栏跟着滚）→ 同一布局栈里 sticky 已被反证有效。
所以**不需要**改成「`.admin-layout` 定高 + `.main` 内部滚动」，那会牵动各页对 `100vh` 的既有假设。

**副作用评估**：侧栏固定在 100vh 后，`.side-nav { flex: 1 }` 的弹性空间让底部用户卡正好贴视口底部
（原代码那句"撑住侧栏高度，避免导航被垂直居中"的注释本就是为此写的）；
`a-dropdown` 浮层默认挂 body，不受 `overflow-y` 影响。医生端与管理员共用此布局，两边同时受益。

## 未读红点 + 已读回执（两端统一）

**需求**：居民端「我的消息」菜单在医生发来消息时显示红点，样式/触发与医生端既有实现一致；

`unreadCount > 0` = 红点（有我没看的，看过即灭）；`awaitingMyReply` = 待回复（有我欠的，回才灭）。

- `ChatPanel`：已读回执只挂在自己**最后一条**消息下；标记已读的三个前置条件
